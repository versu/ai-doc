# 機能テスト(FeatureTest = IntegrationTest)ガイドライン
 
 機能テスト(= 結合テスト / IntegrationTest)に関する、**プログラミング言語に依存しない**基本ガイドライン。
 機能テストは、外部依存のミドルウェア(DB 等)をモックせず、機能(ユースケース)単位の振る舞いを検証するテストを指す。
 
 ---
 
 ## 1. テストで確認する内容
 
 - 正常系(主要シナリオ)
 - 異常系
   - バリデーションエラー・例外
   - 外部依存の失敗(該当する場合)
 
 ---
 
 ## 2. テストメソッドの命名
 
 - **日本語**で記述する。
 - 厳密な命名規則に縛られず、**自由に命名**してよい(規則で表現できることには限界があるため)。
 - **問題領域に精通した非開発者**が読んで、「何を検証しているか」がわかる名前にする。
 - **テスト対象(クラス名・メソッド名・エラーコード名などコード上の識別子)を名前に含めない**。
   - 1つの振る舞いをテストする以上、コード名を入れると実装と密結合するため。
   - ただし、HTTPステータスコード（400,500...etc）は自明なので使用してOK
 
 OK(振る舞いを問題領域の言葉で表現)
 ```
 前提データが揃っていれば正常に登録される
 必須の基準データが無いときは登録されずエラーになる
 ```
 
 NG(コード上の識別子・実装名を含む / 英語のみ)
 ```
 RegisterReturns200WhenValid     // 英語のみ・実装寄り
 CreateUserでpersonがnullになる          // クラス名・メソッド名等、コードに密結合
 ```
 
 ---
 
 ## 3. テスト本文の書き方(AAA)
 
 - 各テストは **Arrange / Act / Assert** の順で記述する。
 - AAA の各ブロックの意図を**インラインコメント**で補足する(メソッド名に込めきれない前提・操作・期待を明示する)。
 
 ```
 テストメソッド() {
     // Arrange: 前提(テストデータ・状態)を準備する
     // Act:     対象の操作を1つ実行する
     // Assert:  結果(戻り値・状態・副作用)を検証する
 }
 ```
 
 ---
 
 ## 4. テストケース(メソッド)の書き方
 
 - **テストケース内で完結させる**。そのテストが何を検証しているかをメソッド本文だけで把握できるよう、多少冗長でも Arrange〜Assert を本文に書く。テスト固有のオーケストレーション(前提データの組み立て・操作・期待値)を private ヘルパーや共通処理に切り出して**共通化しない**。
