# コメント記載ガイドライン

コードコメント（ドキュメントコメント・インラインコメント）の記載ルールをまとめる。
プログラミング言語に依存しない方針とする。

## 基本原則

- **How は書かない**: コードを読めば分かる処理の詳細・型名・メソッド名など、実装の
  逐語的な言い換えは書かない。
- **What は書く**: そのコード／関数が「何をするか（目的・振る舞いの概要）」を書く。
- **Why は分かる場合のみ書く**: なぜそうするか（背景・意図・トレードオフ）が分かる
  場合は書くとよい。任意であり、不明なら無理に書かない。

優先順位は次の通り。

1. まずは明確な命名とコード構造で意図が伝わるようにする。
2. それでも伝わらない「What」をコメントで補う。
3. 知っているなら「Why」を添える。

## ドキュメントコメント

関数・クラス・公開 API の先頭に付けるコメント。

書くこと:

- まず、その関数／クラスが**何をするか**（目的・振る舞いの概要）。
- 補足として、シグネチャから読み取れない情報があれば添える（前提条件・副作用・
  特殊な戻り値の意味など）。型・引数名・null 可否などシグネチャで分かることは書かない。

書かないこと:

- 実装の手順、内部で使う型名・メソッド名の列挙（How）。
- シグネチャから自明な情報の単なる言い換え。

```text
# ❌ 悪い例（How・シグネチャの言い換え）
# UserRepository.findById を呼び、Mapper.toDto で変換して返す。
# 引数 id は整数、戻り値は UserDto。
function getUser(id) { ... }

# ✅ 良い例（What。補足はシグネチャから読み取れない情報のみ）
# ユーザーを取得する。退会済みユーザーも含める。
function getUser(id) { ... }
```

## インラインコメント

処理の途中に挟むコメント。

書くこと:

- 一連の処理ブロックが**何をしているか（What）**の要約。
- 理由（Why）が分かる場合はそれも併記する。

書かないこと:

- 各行の処理を逐語的に言い換える How コメント。

```text
# ❌ 悪い例（コードそのままの言い換え）
stock = stock - 1   # 在庫を 1 減らす

# ✅ 良い例（What。Why が分かれば併記）
# 予約確定に伴い在庫を引き当てる
stock = stock - 1

# ✅ Why を添えた例
# 月末日（31日）に翌月へオーバーフローするのを避けるため日付を補って生成する
date = parse(month + "-01")
```

## 避けるべきコメント（アンチパターン）

- **How の逐語的な言い換え**: コードを読めば分かる内容の繰り返し。
- **コメントアウトされた死コード**: 不要なコードは削除する（履歴はバージョン管理に残る）。
- **陳腐化したコメント**: 実装と乖離したコメント。コード変更時にコメントも更新する。
