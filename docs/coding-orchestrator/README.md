# コーディング オーケストレーター

`/core:coding-orchestrator` スキルの使い方をまとめる。
読者は、ai-doc を導入済みのプロジェクトでオーケストレーターを初めて使う開発者を想定している。

**設定ファイルをプロジェクトごとに一度作っておけば、要件を渡すだけで Pull Request（PR）まで進む。
判断が要る場面では、必ず止まってユーザーに聞く。**

## 何をするものか

オーケストレーターは、依頼を受けてから PR を作るまでの段取りを受け持つスキル。
流れは次のとおり。

1. 仕様を合意する
2. 実装する
3. レビューする
4. PR を作る

実装とレビューは、それぞれ専用のエージェント（**実装エージェント**と**レビュアーエージェント**）に任せる。
オーケストレーター自身はコードを書かず、段取りと、レビュー結果の採否を決める**裁定**だけを行う。
自分で書いたコードを自分で合格にすると、レビューが歯止めにならないため。

使うのは、要件を渡して仕様決めから PR まで任せたいときと、PR に付いたレビューコメントに対応したいとき。
コードを1か所直すだけの依頼には使わない（直接頼むほうが早い）。

## 進み方

依頼は**準備フェーズ**と**実行フェーズ**に分けて進む。

### 準備フェーズ — 何を作るかを合意する

1. 依頼内容と現状の差分、前提をすり合わせる
2. 決まっていない設計判断を1つずつ決める
3. タスクを分けるかを決める（既定は分けない）
4. **spec**（仕様書）の内容を合意する。spec には、今回変えてよい範囲を **Scope lock** として書く
5. Issue を起票し、タスク用のフォルダに spec を書き出す

合意が取れるまで実装には進まない。

### 実行フェーズ — 作ってレビューを通す

タスクごとに次を行う。タスクを分けていなければ1周で終わる。

1. 作業ブランチを切る
2. 実装エージェントが実装してコミットする
3. レビュアーエージェントが差分をレビューする。
   オーケストレーターが指摘を裁定し、**ブロッカー**（直さないと先へ進めない指摘）が残れば実装エージェントに直させて、もう一度レビューする。
   この「レビューして直す」1回を**ラウンド**と呼ぶ
4. テストを流す。画面を作った場合は目視での確認を頼む
5. PR を作る

タスクを分けた場合、2つ目以降のタスクは直前のタスクのブランチから切り、PR の宛先もそのブランチにする（**積み上げ**、stacked PR）。
そのため、PR は古いものから順にマージする。

### ユーザーが判断する場面

判断が要る場面では、選択肢の形で聞かれる。文章を書かずに選べばよい。

| 場面 | 聞かれること |
|---|---|
| 起動したとき | 進行中のタスクがあれば、どれの続きか、新しい依頼か |
| 準備フェーズ | 設計判断、タスクを分けるか、spec の内容でよいか |
| Issue・PR を作る前 | 作ってよいか（設定が `"ask"` のとき） |
| 実装中 | 実装エージェントが仮の判断で進めた点をそれでよいか。Scope lock を越える変更が必要になったときの扱い |
| レビューが上限回数に達したとき | 打ち切って次へ進むか、もう1周回すか |
| 区切りごと | テストの実行コマンド、画面の目視確認の結果 |

## 使う前の準備（プロジェクトごとに1回）

プロジェクトのルートで次を実行し、設定ファイル `.ai/orchestration.json` を作る。

```bash
aidoc orchestrator init
```

`npm link` していない場合は `node <ai-doc>/src/aidoc.js orchestrator init`（`<ai-doc>` は ai-doc をクローンしたフォルダのパス）。
設定が無い状態でオーケストレーターを呼んでも、作成コマンドが案内される。

作ったら、`implementation.docs` と `review.docs` に、そのプロジェクトの規約ファイルを追加する。
`.ai/_docs/`（`aidoc install` が作る、ai-doc の共通規約へのリンク）の規約は既定で読まれるので、書かなくてよい（下の「既定の規約」を参照）。

**設定ファイルが無いと、オーケストレーターは起動しない。**
設定の中身は「このプロジェクトでどの規約を読ませるか」そのもので、既定値のまま進むと、プロジェクトの規約が読まれないまま実装とレビューが終わってしまうため。

## 設定項目

「設定したとき」は、キーを書いた場合に既定値とどう組み合わさるか。**上書き**は書いた値だけが使われ、**既定に追加**は既定の値に書いた値が足される。

| 項目 | 既定値 | 設定したとき | 意味 |
|---|---|---|---|
| `orchestrator.createIssue` | `"ask"` | 上書き | 仕様の合意後に Issue を起票するか。`"ask"` はその都度聞く。`true` / `false` で固定できる |
| `orchestrator.createPullRequest` | `"ask"` | 上書き | タスクが1つ終わるたびに PR を作るか。値の意味は `createIssue` と同じ |
| `implementation.docs` | 下の「既定の規約」 | **既定に追加** | 実装エージェントが着手前に必ず読む規約 |
| `implementation.skills` | なし | 上書き | 実装エージェントに使わせるスキル |
| `review.docs` | 下の「既定の規約」 | **既定に追加** | レビュアーエージェントが読む規約。これがレビューの基準になる |
| `review.skills` | なし | 上書き | レビュアーエージェントに使わせるスキル |
| `review.roundCap` | `3` | 上書き | 1タスクあたりのラウンドの上限 |
| `pullRequest.template` | なし（PR 作成スキルの既定のテンプレート） | 上書き | PR 本文のテンプレート |
| `pullRequest.docs` | なし | 上書き | PR を書く前に読ませる規約。PR 作成スキルの既定の書き方に追加で読ませ、食い違えばこちらを優先する |

### 既定の規約

`implementation.docs` と `review.docs` には、設定に何を書いても次の規約が含まれる。
設定に書いた規約は、この後ろに足される。同じファイルを書いても二重には読まれない。

| ファイル | 内容 | 実装（`implementation.docs`） | レビュー（`review.docs`） |
|---|---|---|---|
| `.ai/_docs/coding.md` | コーディングガイドライン | ○ | ○ |
| `.ai/_docs/comment.md` | コメント記載ガイドライン | ○ | ○ |
| `.ai/_docs/error-handling.md` | エラーハンドリングガイドライン | ○ | ○ |
| `.ai/_docs/feature-test.md` | 機能テストガイドライン | ○ | ○ |
| `.ai/_docs/git-commit-comment.md` | コミットメッセージの書式 | ○ | — |

たとえば PHP のプロジェクトで言語別の規約も読ませたい場合は、次のように足す。

```json
"implementation": { "docs": [".ai/_docs/php-coding.md"] },
"review": { "docs": [".ai/_docs/php-coding.md"] }
```

PR を作るときは、上とは別に PR 作成スキルが自分の既定を使う。

| 用途 | 既定 | 設定との関係 |
|---|---|---|
| PR 本文のテンプレート | [create-gh-pr/references/pr-template.md](../../plugins/core/skills/create-gh-pr/references/pr-template.md) | `pullRequest.template` を設定すると置き換わる |
| PR の書き方の規約 | [create-gh-pr/references/pr-writing.md](../../plugins/core/skills/create-gh-pr/references/pr-writing.md) | 常に読まれる。`pullRequest.docs` はこれに追加で読まれる |

プロジェクトで決まった PR テンプレートや書き方の規約がある場合は、次のように指定する。

```json
"pullRequest": {
  "template": ".github/pull_request_template.md",
  "docs": ["docs/pr-guideline.md"]
}
```

- パスは**リポジトリのルートからの相対パス**で書く。サブフォルダから Claude Code を起動しても同じファイルを指す
- `implementation.skills` に `core:commit` は書かない。`commit` スキルはユーザーの承認を求めるが、実装エージェントはユーザーに質問できないため。コミットメッセージ規約は `implementation.docs` で読ませる

### 設定の検証

オーケストレーターは起動するとまず設定ファイルを検証し、問題があれば理由をすべて示して止まる。
設定を直したあとは、次のコマンドで同じ検証を自分で確かめられる。問題が無ければ終了コード0、あれば理由をすべて示して終了コード1で終わる。

```bash
aidoc orchestrator check
```

止まるのは次のようなとき。

- JSON の構文が誤っている
- キー名を綴り間違えている（`implemntation` など）
- 値の型や範囲が誤っている（`roundCap: 0`、`docs: [1]` など）
- 書いたパスのファイルが無い。既定の規約（`.ai/_docs/...`）が無い場合は、そのプロジェクトで `aidoc install` を実行したかを確認する

各項目の型やパスの解決規則は [references/config.md](../../plugins/core/skills/coding-orchestrator/references/config.md) にある。
既定値の正本は [orchestration.default.json](../../plugins/core/skills/coding-orchestrator/references/orchestration.default.json)。

## 使い方

### 依頼する

要件を添えて頼む。名前で呼ぶ場合は `/core:coding-orchestrator`。

```
オーケストレーターで進めて。受注サマリの月次集計から、キャンセル済みの受注を除外したい
```

### 中断したところから再開する

同じ頼み方で呼び直す。進行中のタスクがあれば一覧が出るので、続けたいものを選ぶ。
どこまで進んだかはタスクのフォルダに記録されているため、セッションをまたいでも続きから再開できる。

### PR のレビューコメントに対応する

「PR にコメントが付いた」と伝えて呼ぶ。どの指摘に対応するかを選ぶと、修正とレビューのあとに既存の PR へ push する。
新しい PR は作らない。

### タスクを完了にする

PR のレビュー対応が済んだら、「タスクを完了にして」と伝える。
タスクのフォルダが `.ai/_tasks/_done/` へ移り、以後は進行中のタスクの一覧に出なくなる。

**完了を伝えるまで、タスクは一覧に残る。** PR を作ったあとは「PR 作成済み」（`pr-created`）として一覧に出るので、レビュー対応のときにそこから選べる。

## 作られるもの

タスクごとに `.ai/_tasks/` の下へフォルダが作られる。`.ai/` は Git の管理対象から除外されているので、プロジェクトのリポジトリには入らない。

```
.ai/_tasks/#42 受注サマリのキャンセル除外/
├── spec.md                               合意した仕様
├── progress.json                         進み具合の記録（再開に使う）
└── #43 キャンセル済みを金額から除く/        タスクを分けた場合。サブ Issue ごとに作られる
    └── spec.md
```

- フォルダ名は `#<Issue 番号> <Issue タイトル>`。Issue を起票しなかった場合は番号なしのタスク名になる
- `progress.json` は手で編集しない。記録の追記と現在状態の更新がずれて、再開できなくなる
- フォルダが `.ai/_tasks/_done/` へ移るのは、タスクを完了にするよう伝えたときだけ。PR を作っただけでは移らない
