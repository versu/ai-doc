# コーディング オーケストレーター

`/core:coding-orchestrator` スキルの使い方をまとめる。
読者は、ai-doc を導入済みのプロジェクトでオーケストレーターを初めて使う開発者を想定している。

**一度導入しておけば、要件を渡すだけで Pull Request（PR）まで進む。
判断が要る場面では、必ず止まってユーザーに聞く。**

## 何をするものか

オーケストレーターは、依頼を受けてから PR を作るまでの段取りを受け持つスキル。
仕様を合意し、実装し、レビューを通して、PR を作る。

実装とレビューは、それぞれ専用のエージェント（**実装エージェント**と**レビュアーエージェント**）に任せる。
オーケストレーター自身はコードを書かず、段取りと、レビューの指摘を採るかどうかの判断（**裁定**）だけを行う。
自分で書いたコードを自分で合格にすると、レビューが歯止めにならないため。

使うのは、要件を渡して仕様決めから PR まで任せたいときと、PR に付いたレビューコメントに対応したいとき。
コードを1か所直すだけの依頼には使わない（直接頼むほうが早い）。

1つのリポジトリ（モノレポを含む）でも、フロントエンドとバックエンドのように分かれた複数のリポジトリでも使える。
違うのは導入の手順だけで、使い方は同じ。

## スタートガイド

見出しや手順に **（任意）** と付いたものは、書いてある場合にだけ行う。付いていないものは必ず行う。

### 1. 導入する

**前提**: オーケストレーターを使うフォルダ（1つのリポジトリで使う場合はそのリポジトリ、複数のリポジトリで使う場合はハブ）で、`aidoc install` を済ませておく。
導入の方法は、ai-doc の [README.md](../../README.md) の「プロジェクトへの導入」を参照する。
ハブの場合は、下の手順2の `aidoc orchestrator init` が、未導入なら `aidoc install` も行うので、先に済ませていなくてもよい。

使い方に合わせて、どちらかを行う。

#### 1つのリポジトリで使う場合（モノレポを含む）

1. リポジトリのルートで、設定ファイルを作る。オーケストレーターと、オーケストレーターが使う Issue 作成スキル・PR 作成スキルの設定ファイルが作られる。
   設定ファイルの詳細は、オーケストレーターは[設定](#設定)、Issue 作成スキルは [docs/create-gh-issue/README.md](../create-gh-issue/README.md#設定任意)、PR 作成スキルは [docs/create-gh-pr/README.md](../create-gh-pr/README.md#設定任意) を参照する

   ```bash
   aidoc orchestrator init
   ```

2. **（任意）** プロジェクト独自の規約（言語別のコーディング規約など）を読ませたい場合は、
   作られた `.ai/_settings/coding-orchestrator/settings.json` の `implementation.docs` と `review.docs` に、その規約ファイルを追加する。
   ai-doc の共通の規約は既定で読まれるので、書かなくてよい（[設定](#設定)を参照）
3. **（任意）** 手順2で設定ファイルを編集した場合は、書き誤りが無いかを確かめる。問題があれば、理由が示される

   ```bash
   aidoc orchestrator check
   ```

   確かめなくても、オーケストレーターが起動時に同じ確認をして、問題があれば止まる

**設定ファイルが無いと、オーケストレーターは起動しない。**
設定は「このプロジェクトでどの規約を読ませるか」そのもので、既定のまま進むと、プロジェクトの規約が読まれないまま実装とレビューが終わってしまうため。

#### 複数のリポジトリを横断して使う場合

VS Code のマルチルートワークスペース（1つのウィンドウで複数のフォルダを開く機能）を使う。
設定とタスクを置くフォルダ（**ハブ**）を、リポジトリとは別に用意し、Claude Code はハブで開く。ハブは Git で管理しなくてよい。

```
workspace-hub/                    ハブ
└── my-project.code-workspace     対象のリポジトリを並べる
api/                              対象のリポジトリ（数と名前は自由に決めてよい）
web/
```

1. VS Code で、ハブと対象のリポジトリを並べたワークスペースを作る
   1. ハブ用のフォルダを作り、VS Code で開く
   2. 「ファイル」>「フォルダーをワークスペースに追加...」から、対象のリポジトリを追加する。リポジトリの数だけ繰り返す
   3. 「ファイル」>「名前を付けてワークスペースを保存...」で、保存先にハブ用のフォルダを選んで保存する。
      ハブに `.code-workspace` ファイル（例: `my-project.code-workspace`）が作られ、`folders` にハブ自身と対象のリポジトリが並ぶ

      ```jsonc
      {
        "folders": [
          { "path": "." },
          { "path": "../api" },
          { "path": "../web" }
        ]
      }
      ```

   リポジトリ名は、`.code-workspace` の `folders` の `name`、無ければフォルダ名になる。
   フォルダ名と違う名前にしたい場合は、保存したファイルを開き、`{ "path": "../web", "name": "front" }` のように `name` を書き足す。
   リポジトリ名はタスクのフォルダ名の先頭に付くので、`#` と空白は使えない
2. ハブで次を実行する。ai-doc の導入、ハブから対象のリポジトリを読み書きできるようにする設定、設定ファイル（オーケストレーターと、Issue 作成スキル・PR 作成スキル）の作成をまとめて行う。
   設定ファイルの詳細は、オーケストレーターは[設定](#設定)、Issue 作成スキルは [docs/create-gh-issue/README.md](../create-gh-issue/README.md#設定任意)、PR 作成スキルは [docs/create-gh-pr/README.md](../create-gh-pr/README.md#設定任意) を参照する

   ```bash
   aidoc orchestrator init
   ```

   終わったら、Claude Code のセッションを開き直す（VS Code 拡張の場合はウィンドウの再読み込み）
3. **（任意）** プロジェクト独自の規約を読ませたい場合は、作られた設定ファイルに規約ファイルを追加する。
   特定のリポジトリだけに読ませる規約（PHP のリポジトリだけの規約など）は `repos` に書く（[設定](#設定)を参照）
4. **（任意）** 手順3で設定ファイルを編集した場合は、`aidoc orchestrator check` で書き誤りが無いかを確かめる

あとからワークスペースにリポジトリを追加したとき、またはリポジトリの場所を変えたときは、ハブで `aidoc workspace sync` を実行し、セッションを開き直す。
忘れていても、オーケストレーターが起動時に気づいて、実行するよう案内する。リポジトリを外したときは実行しなくてよい。

ハブで開いたセッションには、対象のリポジトリの `CLAUDE.md` と `.claude/rules/` が自動では読み込まれない。
オーケストレーターは作業の前にそれらを読むように指示しているが、読むかどうかはモデルが指示に従うかに依存する。
対象のリポジトリの `.claude/settings.json`（権限・hooks）と `.claude/skills/` は効かない。

### 2. 依頼する

要件を添えて頼む。名前で呼ぶ場合は `/core:coding-orchestrator`。

```
オーケストレーターで進めて。受注サマリの月次集計から、キャンセル済みの受注を除外したい
```

依頼内容と現状の差分や、決まっていない設計判断を、選択肢の形で聞かれる。文章を書かずに選べばよい。
推奨案には「（推奨）」が付いている。

作業量が多い場合や、レビューしやすい単位に分けたい場合は、タスクを分けるかも聞かれる（既定は分けない）。
複数のリポジトリにまたがる依頼は、リポジトリごとのタスクに必ず分かれる。1つの PR は1つのリポジトリにしか出せないため。

### 3. spec を確認して合意する

合意した内容は **spec**（仕様書）にまとめられる。
spec の冒頭には、今回変えてよい範囲（目的・やらないこと・受け入れ条件）が **Scope lock** として書かれる。
実装エージェントとレビュアーエージェントは、これを守るべき契約として読む。

spec の下書きは、タスクのフォルダに書き出される。

```
.ai/_tasks/受注サマリのキャンセル除外/
├── spec.md                        spec の下書き
├── progress.json                  進み具合の記録（手で編集しない）
└── キャンセル済みを金額から除く/     タスクを分けた場合。タスクごとに作られる
    └── spec.md
```

内容を確認して、次のどれかを選ぶ。

| 選択肢 | 選ぶとき |
|---|---|
| この内容でよい | 合意する |
| ファイルを編集した | エディタで spec を直した。読み直して、変わった点を確かめてくれる |
| 直したいところを伝える | 直してほしい点を伝えて、直してもらう |

合意すると Issue が作られ（設定により、作ってよいか聞かれる）、フォルダ名に Issue 番号が付く。

```
.ai/_tasks/#42 受注サマリのキャンセル除外/
└── #43 キャンセル済みを金額から除く/
```

複数のリポジトリで使う場合は、フォルダ名の先頭にリポジトリ名が付く。
複数のリポジトリにまたがる依頼では、親の Issue をどのリポジトリに作るか聞かれる。

```
.ai/_tasks/api#42 受注のキャンセル除外/       親の Issue は api に作った
├── api#43 API でキャンセルを除く/
└── front#12 画面でキャンセルを除く/
```

### 4. 実装とレビューを待つ

合意した spec をもとに、タスクごとに実装とレビューが進む。
レビューで直すべき指摘が残っていれば、実装エージェントが直して、もう一度レビューする。

途中で次のことを聞かれる。

| 場面 | 聞かれること |
|---|---|
| ブランチを切るとき | 分岐元のブランチと、作業ブランチの名前 |
| 実装の途中 | 実装エージェントが仮の判断で進めた点をそれでよいか。Scope lock を越える変更が必要になったときの扱い |
| レビューが上限の回数に達したとき | 打ち切って次へ進むか、もう1周回すか |
| タスクの区切り | テストの実行コマンド。画面を作った場合は、目視で確認した結果 |

### 5. PR を確認する

タスクが終わるたびに PR が作られる（設定により、作ってよいか聞かれる）。
すべてのタスクが終わると、作った PR の一覧と、先送りにした指摘の一覧が示される。

タスクを分けた場合、2つ目以降のタスクは直前のタスクのブランチから切られ、PR の宛先もそのブランチになる（**積み上げ**、stacked PR）。
**PR は古いものから順にマージする。**

複数のリポジトリで使う場合は、PR がリポジトリごとに作られる。積み上げは同じリポジトリのタスクの間だけで行う。

### 6. PR のレビューコメントに対応する（任意）

PR にレビューコメントが付き、それに対応したい場合に行う。コメントが付かなければ、手順7へ進む。

「PR にコメントが付いた」と伝えて呼ぶ。指摘ごとに対応するかを選ぶと、修正とレビューのあとに既存の PR へ push される。
新しい PR は作られない。PR への返信は自分で行う（返信の文面は示される）。

### 7. タスクを完了にする

PR のマージなど、そのタスクでやることが無くなったら、「タスクを完了にして」と伝える。
タスクのフォルダが `.ai/_tasks/_done/` へ移り、進行中のタスクの一覧に出なくなる。

**完了を伝えるまで、タスクは一覧に残る。** PR を作っただけでは完了にならないので、レビュー対応のときに一覧から選べる。

### 中断したときは（任意）

セッションを閉じた、別の作業に移ったなどで、途中で止まった場合に行う。

同じ頼み方で呼び直す。進行中のタスクがあれば一覧が出るので、続けたいものを選ぶ。
どこまで進んだかはタスクのフォルダに記録されているので、セッションをまたいでも続きから再開できる。
spec の合意の途中で中断した場合も、下書きから続けられる。

## 設定

設定ファイルは `.ai/_settings/coding-orchestrator/settings.json`。

### 設定項目

「設定したとき」は、キーを書いた場合に既定値とどう組み合わさるか。**上書き**は書いた値だけが使われ、**既定に追加**は既定の値に書いた値が足される。

| 項目 | 既定値 | 設定したとき | 意味 |
|---|---|---|---|
| `orchestrator.createIssue` | `"ask"` | 上書き | spec の合意後に Issue を作るか。`"ask"` はその都度聞く。`true` / `false` で固定できる |
| `orchestrator.createPullRequest` | `"ask"` | 上書き | タスクが1つ終わるたびに PR を作るか。値の意味は `createIssue` と同じ |
| `implementation.docs` | 下の「既定の規約」 | **既定に追加** | 実装エージェントが着手前に必ず読む規約 |
| `implementation.skills` | なし | 上書き | 実装エージェントに使わせるスキル |
| `review.docs` | 下の「既定の規約」 | **既定に追加** | レビュアーエージェントが読む規約。これがレビューの基準になる |
| `review.skills` | なし | 上書き | レビュアーエージェントに使わせるスキル |
| `review.roundCap` | `3` | 上書き | 1タスクあたりのレビューの回数の上限 |
| `repos.<リポジトリ名>.implementation.docs`<br>`repos.<リポジトリ名>.review.docs` | なし | **既定に追加** | 複数のリポジトリで使う場合だけ。そのリポジトリの作業に追加で読ませる規約 |

- パスは、設定ファイルのあるフォルダ（リポジトリのルート、またはハブ）からの相対パスで書く。
  `repos` に書くパスだけは、そのリポジトリのルートからの相対パスで書く
- `implementation.skills` に `core:commit` は書かない。`commit` スキルはユーザーの承認を求めるが、実装エージェントはユーザーに質問できないため。
  コミットメッセージの規約は `implementation.docs` で読ませる

PHP のリポジトリだけ言語別の規約を読ませる場合の例。

```json
"repos": {
  "api": {
    "implementation": { "docs": [".ai/_docs/php-coding.md"] },
    "review": { "docs": [".ai/_docs/php-coding.md"] }
  }
}
```

### 既定の規約

`implementation.docs` と `review.docs` には、設定に何を書いても次の規約が含まれる。
設定に書いた規約は、この後ろに足される。同じファイルを書いても二重には読まれない。

| ファイル | 内容 | 実装 | レビュー |
|---|---|---|---|
| `.ai/_docs/coding.md` | コーディングガイドライン | ○ | ○ |
| `.ai/_docs/comment.md` | コメント記載ガイドライン | ○ | ○ |
| `.ai/_docs/error-handling.md` | エラーハンドリングガイドライン | ○ | ○ |
| `.ai/_docs/feature-test.md` | 機能テストガイドライン | ○ | ○ |
| `.ai/_docs/git-commit-comment.md` | コミットメッセージの書式 | ○ | — |

`.ai/_docs/` は、`aidoc install` が作る ai-doc の共通の規約へのリンク。

### Issue・PR の本文

Issue と PR の本文のテンプレートや追加の規約は、Issue 作成スキルと PR 作成スキルのそれぞれの設定に書く。
スキルを単体で使ったときにも、同じ設定が効くようにするため。どちらの設定ファイルも `aidoc orchestrator init` で作られる。何も書かなければ、スキルに同梱の既定のテンプレートと規約が使われる。

| 用途 | 設定ファイル | 利用ガイド |
|---|---|---|
| Issue の本文 | `.ai/_settings/create-gh-issue/settings.json` | [docs/create-gh-issue/README.md](../create-gh-issue/README.md#設定任意) |
| PR の本文 | `.ai/_settings/create-gh-pr/settings.json` | [docs/create-gh-pr/README.md](../create-gh-pr/README.md#設定任意) |

### 設定に問題があるとき

オーケストレーターは起動するとまず設定を確かめ、問題があれば理由をすべて示して止まる。
Issue 作成スキルと PR 作成スキルの設定も、このとき合わせて確かめる。
直したあとは `aidoc orchestrator check` で確かめられる。

既定の規約（`.ai/_docs/...`）が無いと言われた場合は、`aidoc install` を実行したかを確かめる。

各項目の型やパスの解決の規則は [references/config.md](../../plugins/core/skills/coding-orchestrator/references/config.md) にある。
