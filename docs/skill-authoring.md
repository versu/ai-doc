# スキル作成ガイドライン

本リポジトリのプラグイン（`plugins/<プラグイン名>/`）にスキル・エージェントを追加するときの方針をまとめる。

## 配置

| 種類 | 置き場所 |
|---|---|
| スキル | `plugins/<プラグイン名>/skills/<スキル名>/SKILL.md` |
| エージェント（どのスキルからも使う） | `plugins/<プラグイン名>/agents/<エージェント名>.md` |
| エージェント（特定のスキル専用） | `plugins/<プラグイン名>/skills/<スキル名>/agents/<エージェント名>.md` |
| スキル横断で使うガイド | `plugins/<プラグイン名>/_docs/` |
| そのスキルでしか使わない補助ドキュメント | `plugins/<プラグイン名>/skills/<スキル名>/references/` |
| そのスキルでしか使わないスクリプト | `plugins/<プラグイン名>/skills/<スキル名>/scripts/` |
| スクリプトのテスト | スクリプトと同じ `scripts/`（`<名前>.test.mjs`） |

`agents/` 直下に置くときは、**サブディレクトリで分類しない**。
サブディレクトリ名が呼び出し名の一部になり（`core:review:security` のようになり）、ローカルでの名前と食い違うため。

### 特定のスキル専用のエージェントをコロケーションする

そのスキルからしか起動しないエージェントは、スキルの中に置いたほうが関係が読み取れる。
ただし**既定で読み込まれるのは `agents/` 直下だけ**なので、`plugin.json` の `agents` にファイルを列挙する。

```jsonc
{
  "name": "core",
  "agents": [
    "./skills/coding-orchestrator/agents/implementation.md",
    "./skills/coding-orchestrator/agents/implementation-review.md"
  ]
}
```

- 書けるのは **`./` 始まりのファイルパスだけ**。ディレクトリを書くと `Invalid input` になる
- 呼び出し名はフラットなまま（`core:implementation`）。ディレクトリ名は混入しない
- **`agents` を書くと `agents/` 直下の既定スキャンが無効になる。** 以後はすべてのエージェントを列挙する

**エージェントを追加したら `plugin.json` にも必ず追記する。**
列挙漏れは存在しないものとして扱われ、しかも `claude plugin details` の一覧にも出ないため気づきにくい（`Agents (0)` と表示される）。確認は実セッションで行う。

```bash
claude --plugin-dir plugins/core   # 起動して、利用可能なエージェントを列挙させる
```

## ドキュメントの参照

SKILL.md では `@` によるインポートが使える。相対パスは**作業ディレクトリ基準**で解決されるため、どのプロジェクトから読まれても解決できるよう `${CLAUDE_SKILL_DIR}`（SKILL.md があるディレクトリに置き換わる）を起点に書く。

```markdown
@${CLAUDE_SKILL_DIR}/../../_docs/git-commit-comment.md
```

スキル自身の `references/` を参照するときは、相対リンクでよい。

```markdown
詳細は [references/xxx.md](references/xxx.md) を参照する。
```

## 他のスキル・エージェントを呼び出すスキル

呼び出し名は、読み込まれ方によって変わる。

| 読み込まれ方 | 名前 |
|---|---|
| プラグイン経由（導入先プロジェクト） | `core:implementation-review` |
| ローカル（本リポジトリでの開発中） | `implementation-review` |

どちらでも動くよう、**呼び出し先の名前は SKILL.md の冒頭に表で1回だけ書き**、本文では役割名で参照する。

```markdown
## 呼び出し先

利用可能なスキル・エージェントの一覧を確認し、左の名前があれば左を、なければ右を使う。

| 役割 | 種別 | プラグイン経由の名前 | ローカルの名前 |
|---|---|---|---|
| 実装レビュー | エージェント | `core:implementation-review` | `implementation-review` |
| コミット | スキル | `core:commit` | `commit` |

## 手順

1. 「実装レビュー」エージェントを起動する（名前は上の表で解決する）。
```

呼び出して失敗したら次を試す、という書き方にはしない。失敗した呼び出しの分だけ時間とトークンを消費するため、**呼び出す前に一覧を確認して選ぶ**。

## スクリプトを持つスキル

決まりきった判断（数える、畳み込む、パスを解決する、形を検証する）はスクリプトに寄せる。
AI に任せると、長いセッションで数え間違いや更新漏れが起き、毎回トークンも使う。

- 置き場所は `skills/<スキル名>/scripts/`。テストも同じ場所に `<名前>.test.mjs` で置く
- **依存パッケージを入れない**（`import` は `node:` 始まりのみ）。参画先の環境で動かすため
- 使う API は Node 20 相当に自主規制し、冒頭にバージョンガードを置く
- ファイルの書き込みは一時ファイル + rename で原子的に行う
- テストは `npm test` で回る（`node --test "plugins/**/scripts/*.test.mjs"`）

**スクリプトに判断をさせない。** 合否や分類はスキル側（AI）の責務として残す。
「コマンドが正常終了した」が「合格」を意味しないよう、スクリプトは事実だけを返す。

### SKILL.md から呼ぶ

手順の中で Bash として実行するほか、**インラインシェル構文**で結果を本文に埋め込める。

```markdown
## 起動時点の設定

!`node ${CLAUDE_SKILL_DIR}/scripts/config.mjs show`
```

- `${CLAUDE_SKILL_DIR}` はインラインの中でも展開される
- `allowed-tools` は **`Bash(node:*)` の形**で書く（コマンド名のあとはコロン）。
  `Bash(node *)` のようにスペースで書くと一致しない
- **拒否されると無言で空になる**（権限モードが `plan` のときなど）。
  スキルの実行自体が何も返さずに終わるため、
  **出力が無かった場合に Bash ツールで同じコマンドを実行する**手順を本文に書いておく
- 読み取り専用のコマンドだけをインラインにする。
  インラインはスキルの起動時に必ず走るので、書き込みを混ぜると引数に関係なく実行される

## 振る舞いと規約を分ける

**変える理由が違うものを、同じファイルに混ぜない。**

| 置き場所 | 何を書くか | 変えるとき |
|---|---|---|
| `SKILL.md`（本文） | **振る舞い**。前提の確認、手順、分岐、ユーザーへの確認、停止条件 | 手順が変わったとき |
| `references/*.md` | **規約**。本文の書き方、テンプレート、用語の使い方といった判断の基準 | 基準が変わったとき |
| `_docs/*.md` | **複数のスキルが共有する規約**（コミットメッセージ規約など） | 全体の基準が変わったとき |

本文に規約を複製せず、参照するだけにする（`commit` スキルが「書式の詳細はこのスキルに複製しない＝規約変更に追従させるため」としているのと同じ）。

あわせて次をそろえておくと、スキルが増えたときに読み比べやすい。

| やること | 効く理由 |
|---|---|
| 節の構成をそろえる（目的 / 呼び出し先 / 前提の確認 / 手順 / 停止条件 / 参照） | どのスキルでも同じ場所に同じ種類の情報がある |
| 停止条件を1か所に表で列挙する | 「前提を満たさないなら何もせず止まる」を書き漏らすと、中途半端な状態を作る |
| 出力テンプレートをファイルにする | 形を変えたいとき、テンプレートだけ直せばよい |
| 外部コマンドのバージョン差異と代替経路はスキルの中に閉じる | 呼び出し側が `gh` のバージョンを気にしなくて済む |
| 単体起動の例を本文に1つ書く | 単体で呼べることが担保され、特定の呼び出し元専用に劣化しない |
| 規約ファイルの冒頭に「誰が読むか」を書く | 人間向けの説明とエージェント向けの契約文が混ざるのを防ぐ |

## description の書き方

`description` はスキルが使われるかどうかを決める唯一の手がかりになる。何をするかに加えて、**どういうときに使うか**を具体的に書く。

- ユーザーが実際に打ちそうな言い回しを含める（「コミットして」「変更をコミットして」等）
- 対象外の領域があれば明示する
- 近い領域のスキルがあるときは、どちらを使うかの棲み分けを書く
