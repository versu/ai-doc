# Issue 作成スキル

`/core:create-gh-issue` スキルの使い方をまとめる。
読者は、ai-doc を導入済みのプロジェクトでこのスキルを初めて使う開発者を想定している。

**設定ファイルに書いておけば、プロジェクトで決めたテンプレートと規約で GitHub Issue の本文が書かれる。
スキルを単体で呼んでも、オーケストレーターから呼ばれても、同じ設定が効く。**

## 何をするものか

GitHub に Issue を作るスキル。
親を指定して、その下にぶら下がる子の Issue（GitHub の**サブ Issue** 機能）として作ることもできる。

流れは次のとおり。

1. 前提を確認する（GitHub CLI（`gh` コマンド）にログイン済みか）
2. 本文を組み立てる
3. タイトルと本文を提示し、作ってよいかを聞く
4. Issue を作る。担当者は既定で自分になる

本文を見せずに Issue を作ることはない。
提示された内容は、そのまま作るか、ファイルに書き出して手で直してから作るかを選べる。

次の場面では、止まってユーザーに聞くか、理由を示して止まる。

| 場面 | どうなるか |
|---|---|
| 本文を提示したとき | 作ってよいかを聞かれる |
| 指定した親の Issue が存在しないとき | 作らずに止まる。取り違えた親にぶら下げてしまうため |
| 設定ファイルに問題があるとき | 問題をすべて示して止まる（下の「設定の検証」を参照） |

## 使い方

自然文で頼めばよい。名前で呼ぶ場合は `/core:create-gh-issue`。

```
この不具合を Issue として起票して
```

既定のテンプレートでは、本文は「目的」「やらないこと」「受け入れ条件」の3つで組み立てる。
タイトルは、手段ではなく何を実現するかを1行で書く。

サブ Issue として作るときは、親の Issue 番号を伝える。

```
#42 のサブ Issue として、キャンセル済みの受注を金額から除く Issue を作って
```

サブ Issue を作るには、`gh` 2.94.0 以上と、GitHub.com または GitHub Enterprise Server 3.17 以上が必要。
満たさないときはサブ Issue としては登録せず、子の Issue の本文の先頭に `Parent: #42` の形で親へのリンクを書く。

## 設定（任意）

プロジェクトで決まった Issue のテンプレートや書き方の規約がある場合は、設定ファイルに書く。
**設定ファイルが無くても動く。** そのときはスキルに同梱した既定のテンプレートと規約だけを使う。

設定ファイルの置き場所は `.ai/_settings/create-gh-issue/settings.json`。
`.ai/` は `aidoc install` が Git の管理対象から外しているので、プロジェクトのリポジトリには入らない。
テンプレートや規約のファイルも同じフォルダに置いておくと、Issue 作成スキルに関係するファイルが1か所にまとまる。

プロジェクトのルートで次を実行すると、設定ファイルの雛形が作られる。既にあれば上書きしない。

```bash
aidoc issue init
```

`npm link` していない場合は `node <ai-doc>/src/aidoc.js issue init`（`<ai-doc>` は ai-doc をクローンしたフォルダのパス）。

| 項目 | 既定値 | 意味 |
|---|---|---|
| `template` | `null` | Issue 本文のテンプレートのパス。`null` なら既定のテンプレートを使う |
| `docs` | `[]` | 本文を書く前に追加で読ませる規約のパスの配列 |

既定のテンプレートと規約とは、次のように組み合わさる。

| 用途 | 既定 | 設定との関係 |
|---|---|---|
| 本文のテンプレート | [issue-template.md](../../plugins/core/skills/create-gh-issue/references/issue-template.md) の雛形 | `template` を書くと置き換わる。置き換わるのは本文の構成だけで、同じファイルにある方針（仕様書の全文を貼らない）とタイトルの書き方は引き続き守られる |
| 書き方の規約 | [technical-writing.md](../../plugins/core/_docs/technical-writing.md)（テクニカルライティング規約） | 常に読まれる。`docs` はこれに追加で読まれ、食い違えば `docs` が優先される |

`docs` を優先するのは、プロジェクトで決めた規約のほうが、既定の一般的な基準より具体的なため。

設定の例を示す。

```json
{
  "template": ".ai/_settings/create-gh-issue/template.md",
  "docs": [".ai/_settings/create-gh-issue/issue-rule.md"]
}
```

- パスは**リポジトリのルートからの相対パス**で書く。サブフォルダから Claude Code を起動しても同じファイルを指す
- 絶対パスと、`~` で始まるホームフォルダからのパスも書ける

### 設定の検証

スキルは起動時に設定ファイルを検証し、問題があれば理由をすべて示して止まる。
読ませるはずのテンプレートや規約が無いまま本文を書くと、プロジェクトの決まりに沿わない Issue ができてしまうため。

設定を書いたら、次のコマンドで同じ検証を確かめられる。
問題が無ければ終了コード0、あれば理由をすべて示して終了コード1で終わる。

```bash
aidoc issue check
```

止まるのは次のようなとき。

- JSON の構文が誤っている
- キー名を綴り間違えている（`tempalte` など）
- 値の型が誤っている（`template: 1`、`docs: "rule.md"` など）
- 書いたパスのファイルが無い

## オーケストレーターから使うとき

[オーケストレーター](../coding-orchestrator/README.md)（`/core:coding-orchestrator`）は、仕様を合意したあとにこのスキルを呼んで Issue を起票する。
このときも、上の設定ファイルがそのまま使われる。オーケストレーター側に Issue の設定は無い。

オーケストレーターは起動時に、この設定ファイルも合わせて検証する。
仕様の合意まで進んでから Issue の起票で初めて設定の誤りに気づく、ということが起きないようにするため。
