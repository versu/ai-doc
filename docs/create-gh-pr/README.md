# PR 作成スキル

`/core:create-gh-pr` スキルの使い方をまとめる。
読者は、ai-doc を導入済みのプロジェクトでこのスキルを初めて使う開発者を想定している。

**設定ファイルに書いておけば、プロジェクトで決めたテンプレートと規約で Pull Request（PR）の本文が書かれる。
スキルを単体で呼んでも、オーケストレーターから呼ばれても、同じ設定が効く。**

## 何をするものか

作業ブランチを GitHub へ push し、PR を作るスキル。
本文は、変更の背景を知らない人間のレビュアーが読む前提で、コードの内部名ではなく業務の言葉（ドメイン用語）で書く。

流れは次のとおり。

1. 前提を確認する（GitHub CLI（`gh` コマンド）にログイン済みか、未コミットの変更が無いか、コミットが1つ以上あるか）
2. 本文を組み立てる
3. タイトルと本文を提示し、作ってよいかを聞く
4. 宛先（base）ブランチを最新にし、更新があれば作業ブランチを rebase する
5. 作業ブランチを push する
6. PR を作る

本文を見せずに PR を作ることはない。
提示された内容は、そのまま作るか、ファイルに書き出して手で直してから作るかを選べる。

次の場面では、止まってユーザーに聞くか、理由を示して止まる。

| 場面 | どうなるか |
|---|---|
| 本文を提示したとき | 作ってよいかを聞かれる |
| 作業ブランチが既にリモートにあり、base に更新があるとき | rebase して強制 push するか、rebase せずに進めるかを聞かれる |
| rebase で競合したとき | rebase を取り消して止まる。競合の解き方はコードの意図に関わるため |
| 設定ファイルに問題があるとき | 問題をすべて示して止まる（下の「設定の検証」を参照） |

## 使い方

自然文で頼めばよい。名前で呼ぶ場合は `/core:create-gh-pr`。

```
PR を作って
```

宛先ブランチを指定しなければ、リポジトリの既定ブランチ（`main` など）が宛先になる。

前の PR のブランチから続けて切ったブランチ（**積み上げ**、stacked PR）の場合は、前の PR のブランチを宛先に指定する。
このとき PR の本文に、どの PR の上に積んでいるかとマージの順番が書かれる。

```
feature/#42-cancel-exclude を宛先にして PR を作って
```

対応する Issue が別のリポジトリにある場合は、`versu/ai-doc#42` のようにリポジトリ名を付けて伝える。
番号だけだと、PR と同じリポジトリの Issue として扱われる。

## 設定（任意）

プロジェクトで決まった PR のテンプレートや書き方の規約がある場合は、設定ファイルに書く。
**設定ファイルが無くても動く。** そのときはスキルに同梱した既定のテンプレートと規約だけを使う。

設定ファイルの置き場所は `.ai/_settings/create-gh-pr/settings.json`。
`.ai/` は `aidoc install` が Git の管理対象から外しているので、プロジェクトのリポジトリには入らない。
テンプレートや規約のファイルも同じフォルダに置いておくと、PR 作成スキルに関係するファイルが1か所にまとまる。

プロジェクトのルートで次を実行すると、設定ファイルの雛形が作られる。既にあれば上書きしない。

```bash
aidoc pr init
```

`npm link` していない場合は `node <ai-doc>/src/aidoc.js pr init`（`<ai-doc>` は ai-doc をクローンしたフォルダのパス）。

| 項目 | 既定値 | 意味 |
|---|---|---|
| `template` | `null` | PR 本文のテンプレートのパス。`null` なら既定のテンプレートを使う |
| `docs` | `[]` | 本文を書く前に追加で読ませる規約のパスの配列 |

既定のテンプレートと規約とは、次のように組み合わさる。

| 用途 | 既定 | 設定との関係 |
|---|---|---|
| 本文のテンプレート | [pr-template.md](../../plugins/core/skills/create-gh-pr/references/pr-template.md) | `template` を書くと置き換わる。テンプレートで決まるのは本文の構成だけで、タイトルは別に起こされる |
| 書き方の規約 | [pr-writing.md](../../plugins/core/skills/create-gh-pr/references/pr-writing.md) | 常に読まれる。`docs` はこれに追加で読まれ、食い違えば `docs` が優先される |

`docs` を優先するのは、プロジェクトで決めた規約のほうが、既定の一般的な基準より具体的なため。

設定の例を示す。

```json
{
  "template": ".ai/_settings/create-gh-pr/template.md",
  "docs": [".github/pr-guideline.md"]
}
```

- パスは**リポジトリのルートからの相対パス**で書く。サブフォルダから Claude Code を起動しても同じファイルを指す
- 絶対パスと、`~` で始まるホームフォルダからのパスも書ける

### 設定の検証

スキルは起動時に設定ファイルを検証し、問題があれば理由をすべて示して止まる。
読ませるはずのテンプレートや規約が無いまま本文を書くと、プロジェクトの決まりに沿わない PR ができてしまうため。

設定を書いたら、次のコマンドで同じ検証を確かめられる。
問題が無ければ終了コード0、あれば理由をすべて示して終了コード1で終わる。

```bash
aidoc pr check
```

止まるのは次のようなとき。

- JSON の構文が誤っている
- キー名を綴り間違えている（`tempalte` など）
- 値の型が誤っている（`template: 1`、`docs: "rule.md"` など）
- 書いたパスのファイルが無い

## オーケストレーターから使うとき

[オーケストレーター](../coding-orchestrator/README.md)（`/core:coding-orchestrator`）は、タスクごとの最後にこのスキルを呼んで PR を作る。
このときも、上の設定ファイルがそのまま使われる。オーケストレーター側に PR の設定は無い。

オーケストレーターは起動時に、この設定ファイルも合わせて検証する。
実装とレビューを終えたあとの PR 作成で初めて設定の誤りに気づく、ということが起きないようにするため。
