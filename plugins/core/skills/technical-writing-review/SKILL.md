# 技術文書のレビュー

## 参照

テクニカルライティング規約（毎回その時点の最新内容が取り込まれる）。指摘の観点はすべてこの規約に従う。

@${CLAUDE_SKILL_DIR}/../../_docs/technical-writing.md

報告の書式は [references/report-format.md](references/report-format.md) に従う。

## レビュー方針

- **推敲レベルは文書の種類相応にとどめる。** 基準は「技術的な内容が正しく伝わり、読者がスムーズに読めること」
- **表現の好みは指摘しない。** 弱い言い回し（「〜かもしれません」「〜と思います」など）の言い換えも求めない
- 文体・語尾の揺れは指摘しない。ただし**過度なキャラ付けは見つけたら必ず指摘する**
- 論理構成の一貫性と、初見の読者が理解できるかを重視する

## 手順

**下の「停止条件」に当たったら、レビューせずに理由を伝えて止まる。**

### 1. 対象と読者を確認する

対象の原稿、文書の種類、想定読者を決める。
想定読者は規約の「読者の基準」の表から既定を取り、依頼に別の指定があればそれに従う。

### 2. 初見読者シミュレーション

通読の前に、初めてその話題に触れる読者が途中の一語で詰まらないかを確かめる。

1. **用語の棚卸し**: 規約の「用語」の分類に当たるものを原稿から抜き出し、それぞれについて次を確認する
   - 初出の位置（見出し・キャプションを含む）
   - 説明の有無（フルスペル・言い換え・脚注・1文の補足）
   - 説明の順序（説明が初出の箇所か、それより前にあるか）
2. **前提の飛躍**: 規約の「論理構成」「図表」に沿って、選択の理由、図表の読み解きやすさ、概念と具体例の対応を確認する

用語の指摘は「初出箇所／現状／補える1文の案」をセットにし、**詰まりやすい順**に並べる。
補足案は著者の文体に合わせ、そのまま挿入できる形で書く。

### 3. 通読レビュー

原稿を通読し、規約の各節（文体・用語・文・表記・論理構成・全体構成・図表）を観点として評価する。

### 4. 報告する

[references/report-format.md](references/report-format.md) の書式でまとめて返す。

## 停止条件

| 条件 | 理由 |
|---|---|
| 対象の原稿が特定できない | どれを読めばよいか分からないため |

## 単体起動の例

```
docs/articles/ocr-benchmark.md をレビューして。読者は社外のエンジニア
```
