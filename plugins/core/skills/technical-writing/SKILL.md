# 技術文書の執筆

## 参照

テクニカルライティング規約（毎回その時点の最新内容が取り込まれる）。
判断の基準はすべてこの規約に従い、このスキルには複製しない。

@${CLAUDE_SKILL_DIR}/../../_docs/technical-writing.md

## 手順

**下の「停止条件」に当たったら、書かずに理由を伝えて止まる。**

### 1. 前提を確認する

次の4つを決める。依頼から読み取れないものは `AskUserQuestion` で聞く。

| 項目 | 決め方 |
|---|---|
| 文書の種類 | 規約の「読者の基準」の表のどれに当たるか |
| 想定読者 | 種類から決まる既定の読者でよいか。社外向けか社内向けか |
| 目的 | 読み終えた読者が何を分かる・できるようになるか |
| 出力先 | ファイルパス。既存ファイルなら上書きか追記か |

### 2. 骨子を提示して合意を取る

本文を書く前に、次を提示する。**骨子の合意なしに本文を書かない**（構成の手戻りは本文の手直しより重いため）。

- 見出し構成と、各節で言うこと（1行ずつ）
- 冒頭で述べる主張と、まとめで述べる主張（ずれていないこと）
- 図表を使う場合は、どの節に何を置くか

### 3. 用語リストを作る

規約の「用語」の分類に沿って、文書に出てくる説明が必要な用語を洗い出し、
**どこで初出になり、どう説明するか**を決めておく。書きながら決めると、説明が初出より後ろにずれやすい。

### 4. 書く

骨子と用語リストに沿って書き、出力先に保存する。

### 5. 自己点検してから渡す

規約の各節を観点として読み直し、当てはまる箇所を直す。
渡すときは、点検で直した主な点を短く添える（直す必要がなかったなら、その旨だけでよい）。

## 停止条件

| 条件 | 理由 |
|---|---|
| 想定読者または出力先が決まらない | 読者が決まらないと用語の説明の要否が決まらず、出力先が無いと渡せないため |
| 既存ファイルを上書きすることになり、確認が取れていない | 手元の文章を失うため |

## 単体起動の例

```
.ai/_tasks/foo/ の設計メモをもとに、新メンバー向けの README を docs/README.md に書いて
```
