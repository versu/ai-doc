# spec.md の雛形

読み手はオーケストレーター。タスクごとにこの形で書く。

下書きの間（`progress.json` の `phase` が `preparation`）は、タイトルの直後に下の印を置く。
ユーザーがファイルを開いたときに、合意済みと取り違えないようにするため。
**合意したら印を外す。** 合意済みかどうかの正は `phase` で、印は人が見て分かるようにするためのもの。

```markdown
> **下書き（未合意）** — 内容を直す場合は、このファイルを編集してからオーケストレーターに伝える
```

```markdown
# <タスク名>

## Scope lock

**この節は合意した内容の固定であり、変更には再合意を要する。**

### 目的
（このタスクで何を達成するのか。1〜3文）

### やらないこと
- （明示的に範囲外とするもの）
- （今回は触らないと合意したもの）

### 受け入れ条件
- [ ] 設定で無効にしている対象には作成できない
- [ ] 同じ内容の重複は弾く
- [ ] 途中で失敗してロールバックしたときは通知を飛ばさない

---

## 背景・経緯
（認識合わせで確定した前提）

## 設計判断
| 論点 | 決定 | 理由 |
|---|---|---|

## 詳細仕様書
（DB スキーマ・API のインターフェースを変えるときだけ。無ければ節ごと削る）
- [DB 設計](db-design.md) — 追加・変更するテーブルと列、ER 図
- [API 定義](openapi.yaml) — 新規 API のリクエストとレスポンス

## 影響範囲
（触るファイル・モジュールの見当）

## 補足
（未確定のまま進める事項があれば、仮置きの判断と根拠）
```

## 書き方

- **文章はテクニカルライティング規約に沿って書く。** 規約は SKILL.md の STEP 3 に取り込まれている。
  spec は合意するユーザーが読む文書でもあり、調査中に使っていた略語・内部の呼び名・
  コード上の識別子を説明なしに並べると、ユーザーが合意の判断をできない
- **Scope lock は冒頭に固定する。** 実装エージェントもレビュアーも、この3つを
  「守るべき契約」として読む。位置が動くと読み落とされる
- **列名・プロパティ名の単位の内容は spec に書かず、詳細仕様書に分ける**（[detailed-spec.md](detailed-spec.md)）。
  spec からは「詳細仕様書」の節でリンクする。実装エージェントとレビュアーはこのリンクをたどって読むので、
  リンクが無い詳細仕様書は読まれない。サブタスクの spec からは `../db-design.md` のように親フォルダを指す
- 受け入れ条件は**1タスクにつき数件**。多すぎるならタスクの切り方が粗い
- 受け入れ条件は**振る舞いで書く**。「〇〇クラスを作る」のような実装手段では書かない。
  手段で書くと、それを作りさえすれば条件を満たしたことになってしまう

悪い例と良い例。

| ❌ 手段で書いている | ⭕ 振る舞いで書いている |
|---|---|
| `RegisterValidator` クラスを追加する | 設定で無効にしている対象には作成できない |
| 一意制約を張る | 同じ内容の重複は弾く |
| トランザクションで囲む | 途中で失敗してロールバックしたときは通知を飛ばさない |
