# spec.md の雛形

読み手はオーケストレーター。タスクごとにこの形で書く。
**合意が取れるまでファイルとして書き出さない。** 書いてあると合意済みに見えてしまうため、
草案は会話の中で提示する。

```markdown
# <タスク名>

## Scope lock

**この節は合意した内容の固定であり、変更には再合意を要する。**

### 目的
（このタスクで何を達成するのか。1〜3文）

### やらないこと
- （明示的に範囲外とするもの）
- （今回は触らないと合意したもの）

### 受け入れ条件
- [ ] 設定で無効にしている対象には作成できない
- [ ] 同じ内容の重複は弾く
- [ ] 途中で失敗してロールバックしたときは通知を飛ばさない

---

## 背景・経緯
（認識合わせで確定した前提）

## 設計判断
| 論点 | 決定 | 理由 |
|---|---|---|

## 影響範囲
（触るファイル・モジュールの見当）

## 補足
（未確定のまま進める事項があれば、仮置きの判断と根拠）
```

## 書き方

- **Scope lock は冒頭に固定する。** 実装エージェントもレビュアーも、この3つを
  「守るべき契約」として読む。位置が動くと読み落とされる
- 受け入れ条件は**1タスクにつき数件**。多すぎるならタスクの切り方が粗い
- 受け入れ条件は**振る舞いで書く**。「〇〇クラスを作る」のような実装手段では書かない。
  手段で書くと、それを作りさえすれば条件を満たしたことになってしまう

悪い例と良い例。

| ❌ 手段で書いている | ⭕ 振る舞いで書いている |
|---|---|
| `RegisterValidator` クラスを追加する | 設定で無効にしている対象には作成できない |
| 一意制約を張る | 同じ内容の重複は弾く |
| トランザクションで囲む | 途中で失敗してロールバックしたときは通知を飛ばさない |
