# 準備フェーズの手順

読み手はオーケストレーター。

**仕様と依頼内容の突き合わせ／未確定の設計判断／タスク分解／spec の合意**をユーザーと確定し、
`progress.json` を初期化するまでがこのフェーズ。

ここで合意なしに先へ進むと、あとで「そういうつもりではなかった」が実装のやり直しになる。
合意した内容は必ず spec に書く。セッションが切れても再現できるようにするため。

**合意は `AskUserQuestion` で取る。** 本文に質問を書いて返事を待つ形にしない。
自動で回している最中の地の文の質問は流されやすく、こちらが勝手に答えを決めてしまう。
選択肢の作り方は SKILL.md の「ユーザーの合意は `AskUserQuestion` で取る」にまとめてある。

## 1. 初期化

設定の確認と、状態ファイルによる再開位置の判定は SKILL.md の STEP 1・2 で済んでいる。

タスクフォルダと spec は、**Issue を起票する前に下書きとして作る**（5 を参照）。
ユーザーが spec をエディタで直してから合意できるようにするためで、
中断しても下書きが残るので、再開したら下書きから続けられる。

**合意済みかどうかは `progress.json` の `phase` で決まる**（`preparation` の間は未合意）。
ファイルがあることを、合意済みの意味に取らない。

## 2. 認識合わせ

既存の spec と関連コードを調べ、依頼内容との差分・前提をユーザーに確認する。
ここで拾うのは「依頼の文面からは読み取れないが、実装すると必ずぶつかること」。

**複数リポジトリモード**（起動時点の設定の `mode` が `multi`）では、どのリポジトリに関わる依頼かもここで確定する。
関わるリポジトリの `CLAUDE.md`・`.claude/CLAUDE.md`・`.claude/rules/**/*.md` を読んでから spec を書く。
ハブで開いたセッションでは、対象リポジトリの規約が自動では読み込まれないため。

## 3. 未確定の設計判断

論点ごとに `AskUserQuestion` を出し、**推奨案を先頭に置いて**決めてもらう。
選択肢を並べるだけだと判断を丸投げすることになるので、必ず推し案と理由を添える。
推奨案のラベルには「（推奨）」を付ける。

## 4. タスク分解 — 既定は「分解しない」

**分解は例外であって既定ではない。** 1体の実装エージェントが最後まで担当できるなら、
分けるほど引き継ぎのコストと状態管理の複雑さが増えるだけになる。

分解を検討するのは次のどちらかのときだけ。

| # | 理由 | 判断 |
|---|---|---|
| 1 | 1体の実装エージェントのコンテキストに収まらない分量 | 下の目安を使う。これが本来の分解理由 |
| 2 | 人間がレビューしやすい単位で PR を分けたい | ユーザーの希望。分量が収まっていても分けてよい |
| 3 | 複数のリポジトリにまたがる（複数リポジトリモード） | **必ず分解する。** 1つの PR は1つのリポジトリにしか出せないため。リポジトリごとに少なくとも1タスク |

### 分量の見積もりの目安

正確には測れないので、次の兆候が**複数**当てはまるときに分解を提案する。
1つ当てはまった程度では分解しない。

- 実装の前に読む必要のある既存コードが広い（複数の層・モジュールにまたがる）
- 受け入れ条件が10件を超える
- 「まず〇〇を用意してから、それを使って△△を作る」のように、
  前半の成果が固まらないと後半に着手できない段取りがある
- 触るファイルが多く、1つのコミットで意図を説明しきれない

**迷ったら分解しない。** 進めてみて収まらないと分かった時点で残りを新しいタスクとして
切り出すほうが、最初から細かく割るより無駄が少ない。

**分解しないことも合意事項。** 「分けなくてよいか」を `AskUserQuestion` で必ず1度は聞く
（人間のレビュー単位という理由での分割希望を拾うため）。
選択肢は「分けない（推奨）」／「分ける」。

分解する場合、サブタスクのフォルダも親フォルダの中に作る（5-1 参照）。

### 複数リポジトリにまたがるときの親

親 Issue を立てる**主リポジトリ**を `AskUserQuestion` で決める。ハブは git 管理しないので、親 Issue はどれかのリポジトリに立てる。
推奨は、変更の起点になるリポジトリ（例: API を足して画面から使うなら API 側）。
サブタスクの順序は、依存される側（API など）を先に並べる。

## 5. spec の下書きと合意

### 5-1. 下書きのタスクフォルダを作る

フォルダ名は、Issue 番号を付けない **`<タイトル>`**。番号は Issue を起票したあとに 6-2 で付ける。

```
.ai/_tasks/受注サマリのキャンセル除外/
├── spec.md
├── progress.json
└── キャンセル済みを金額から除く/     ← 分解した場合。サブタスクごと
    └── spec.md
```

既にある Issue に取り組む場合は、最初から **`#<Issue 番号> <Issue タイトル>`** で作り、6-2 の改名はしない。

**複数リポジトリモード**では、親もサブタスクも**名前の先頭にリポジトリ名と空白**を付ける。
親は主リポジトリの名前。リポジトリ名は起動時点の設定の `repos` のキー。

```
.ai/_tasks/api 受注のキャンセル除外/
├── spec.md
├── progress.json
├── api API でキャンセルを除く/
│   └── spec.md
└── web 画面でキャンセルを除く/
    └── spec.md
```

番号を付けると `api#42 受注のキャンセル除外`・`web#12 画面でキャンセルを除く` のようになる。
既にある Issue に取り組む場合は、最初から `<リポジトリ>#<Issue 番号> <Issue タイトル>` で作る。

フォルダ名に空白と `#` が入ることがあるので、**以後パスを渡すときは必ず引用符で囲む**。

### 5-2. spec と状態ファイルを書き出す

1. タスクごとに spec の下書きを書き出す（[spec-template.md](spec-template.md)）。冒頭に下書きの印を付ける。
   文章は SKILL.md の STEP 3 に取り込まれているテクニカルライティング規約に沿って書き、
   書いたあとに規約の各節を観点として読み直す
2. **DB スキーマまたは API のインターフェースを変えるタスクなら、詳細仕様書も書き出す**
   （[detailed-spec.md](detailed-spec.md)）。当てはまるかは毎回確かめる。
   置き場所は親のタスクフォルダの直下で、使うタスクの spec の「詳細仕様書」の節からリンクする
3. `tasks.json` を組み立てる。**`id` はサブタスクのフォルダ名と同じにする**。分解していなければ `[]`

```json
[{ "id": "キャンセル済みを金額から除く", "title": "キャンセル済みを金額から除く", "issue": null }]
```

4. `progress.json` を作る。この時点の `phase` は `preparation`

```bash
node <このスキル>/scripts/state.mjs init --dir ".ai/_tasks/受注サマリのキャンセル除外" --tasks tasks.json
```

**複数リポジトリモード**では、`tasks.json` の各タスクに `repo` を足し、`init` に `--repo <主リポジトリ>` を渡す。
分解しなかった（1つのリポジトリで閉じる）場合も `--repo` は必須。ワークスペースに無い名前や指定漏れは `init` が弾く。

```json
[{ "id": "api API でキャンセルを除く", "title": "API でキャンセルを除く", "issue": null, "repo": "api" },
 { "id": "web 画面でキャンセルを除く", "title": "画面でキャンセルを除く", "issue": null, "repo": "web" }]
```

```bash
node <このスキル>/scripts/state.mjs init --dir ".ai/_tasks/api 受注のキャンセル除外" --tasks tasks.json --repo api
```

### 5-3. 合意を取る

spec のパス（詳細仕様書を作ったならそのパスも）を示し、`AskUserQuestion` で次を聞く。

| 選択肢 | すること |
|---|---|
| この内容でよい | 6 へ進む |
| ファイルを編集した | ファイルを読み直し、変わった点を要約してもう一度聞く |
| 直したいところを伝える | 聞いた内容を spec と詳細仕様書に反映し（文章は 5-2 と同じく規約に沿って書く）、もう一度聞く |

**聞くたびに、ファイルの現在の内容を読み直す。** ユーザーがエディタで直していることがあり、
手元に持っている内容を使い回すと、その編集を取りこぼす。

特に合意が要るのは **Scope lock の3つ**（目的・やらないこと・受け入れ条件）。
ここが実装エージェントとレビュアーへの契約になり、以後の変更には再合意が必要になる。

## 6. 確定

### 6-1. Issue を起票する

設定に従う（`"ask"` なら `AskUserQuestion` でここで聞く）。

- 分解した場合は**親 Issue とサブ Issue**。分解しなければ Issue は1本
- 本文には spec の **Scope lock だけ**を載せる。全文を二重化しない。**ファイルの現在の内容から取る**
- 起票は Issue 作成スキルに委譲する

**複数リポジトリモード**では、親 Issue は主リポジトリに、サブ Issue はそれぞれのタスクのリポジトリに立てる。
Issue 作成スキルには作業リポジトリ（`repos.<リポジトリ>.path`）と、タスクフォルダの絶対パスを渡す。
親と別のリポジトリに立てるサブ Issue は、親を `owner/repo#番号` の形で渡す。スキルは `--parent` で紐付けずに作成した Issue の参照を返すので、
親 Issue の本文にサブ Issue へのリンク（`owner/repo#12`）を足す（`gh issue edit` は親のリポジトリで実行する）。

### 6-2. フォルダに Issue 番号を付ける

起票したら、番号を標準入力で渡してフォルダを改名する。
親とサブタスクのフォルダ名、`tasks[].id`・`tasks[].issue` の書き換えはこのコマンドがまとめて行う。
**自分でフォルダを改名しない。** 名前の書式が揺れるうえ、`tasks[].id` との食い違いで再開が壊れる。

```bash
echo '{"parent":42,"tasks":{"キャンセル済みを金額から除く":43}}' \
  | node <このスキル>/scripts/state.mjs assign-issues --dir ".ai/_tasks/受注サマリのキャンセル除外"
```

- 改名後のパスは戻り値の `to` にある。以後はそちらを使う
- 複数リポジトリモードの番号付け（`api 受注…` → `api#42 受注…`）も、このコマンドが `repo` を見て行う
- 失敗したら（改名先に同名のフォルダがある、など）何も変わっていないので、理由を伝えて止まる
- Issue を起票しなかった場合は改名しない（フォルダ名は `<タイトル>` のまま）
- 改名できるのは `agreement` を追記する前だけ。順番を逆にしない

実行順序は名前ではなく `progress.json` の `tasks` 配列の並びで決まるので、番号が飛んでいても問題ない。

### 6-3. 合意を記録する

1. spec と詳細仕様書の下書きの印を外す
2. `agreement` の履歴を追記する。これで `phase` が `execution` になる

```bash
echo '{"kind":"agreement","task":null,"data":{"summary":"<何に合意したか>","parentIssue":42}}' \
  | node <このスキル>/scripts/state.mjs append --dir ".ai/_tasks/#42 受注サマリのキャンセル除外"
```

準備完了を報告し、実行フェーズへ進んでよいか確認する。
