# 準備フェーズの手順

読み手はオーケストレーター。

**仕様と依頼内容の突き合わせ／未確定の設計判断／タスク分解／spec の合意**をユーザーと確定し、
`progress.json` を初期化するまでがこのフェーズ。

ここで合意なしに先へ進むと、あとで「そういうつもりではなかった」が実装のやり直しになる。
合意した内容は必ず spec に書く。セッションが切れても再現できるようにするため。

**合意は `AskUserQuestion` で取る。** 本文に質問を書いて返事を待つ形にしない。
自動で回している最中の地の文の質問は流されやすく、こちらが勝手に答えを決めてしまう。
選択肢の作り方は SKILL.md の「ユーザーの合意は `AskUserQuestion` で取る」にまとめてある。

## 1. 初期化

設定の確認と、状態ファイルによる再開位置の判定は SKILL.md の STEP 1・2 で済んでいる。

**このフェーズではファイルを1つも作らない。** タスクフォルダも spec も、
すべて 6 の確定でまとめて作る。フォルダ名に Issue 番号を入れるため、
Issue を起票するまで名前が決まらないからでもある。

その代わり、**準備フェーズの途中で中断すると、合意の経過は残らない**。
再開したら会話からやり直すことになる。長引きそうなら、
論点を小さく切って先に確定させるほうがよい。

## 2. 認識合わせ

既存の spec と関連コードを調べ、依頼内容との差分・前提をユーザーに確認する。
ここで拾うのは「依頼の文面からは読み取れないが、実装すると必ずぶつかること」。

## 3. 未確定の設計判断

論点ごとに `AskUserQuestion` を出し、**推奨案を先頭に置いて**決めてもらう。
選択肢を並べるだけだと判断を丸投げすることになるので、必ず推し案と理由を添える。
推奨案のラベルには「（推奨）」を付ける。

## 4. タスク分解 — 既定は「分解しない」

**分解は例外であって既定ではない。** 1体の実装エージェントが最後まで担当できるなら、
分けるほど引き継ぎのコストと状態管理の複雑さが増えるだけになる。

分解を検討するのは次のどちらかのときだけ。

| # | 理由 | 判断 |
|---|---|---|
| 1 | 1体の実装エージェントのコンテキストに収まらない分量 | 下の目安を使う。これが本来の分解理由 |
| 2 | 人間がレビューしやすい単位で PR を分けたい | ユーザーの希望。分量が収まっていても分けてよい |

### 分量の見積もりの目安

正確には測れないので、次の兆候が**複数**当てはまるときに分解を提案する。
1つ当てはまった程度では分解しない。

- 実装の前に読む必要のある既存コードが広い（複数の層・モジュールにまたがる）
- 受け入れ条件が10件を超える
- 「まず〇〇を用意してから、それを使って△△を作る」のように、
  前半の成果が固まらないと後半に着手できない段取りがある
- 触るファイルが多く、1つのコミットで意図を説明しきれない

**迷ったら分解しない。** 進めてみて収まらないと分かった時点で残りを新しいタスクとして
切り出すほうが、最初から細かく割るより無駄が少ない。

**分解しないことも合意事項。** 「分けなくてよいか」を `AskUserQuestion` で必ず1度は聞く
（人間のレビュー単位という理由での分割希望を拾うため）。
選択肢は「分けない（推奨）」／「分ける」。

分解する場合、サブタスクのフォルダ名もサブ Issue から作る（6-2 参照）。

## 5. spec の合意

タスクごとに spec の草案を提示し、`AskUserQuestion` で
「この内容でよい」／「直したいところがある」を聞く。
指摘があれば反映してもう一度聞き、合意できてから確定させる（[spec-template.md](spec-template.md)）。

**合意前の spec をファイルとして書き出さない。** 書いてあると合意済みに見えてしまう。

特に合意が要るのは **Scope lock の3つ**（目的・やらないこと・受け入れ条件）。
ここが実装エージェントとレビュアーへの契約になり、以後の変更には再合意が必要になる。

## 6. 確定

**Issue を先に起票する。** フォルダ名に Issue 番号を使うため、順番が逆にできない。

### 6-1. Issue を起票する

設定に従う（`"ask"` なら `AskUserQuestion` でここで聞く）。

- 分解した場合は**親 Issue とサブ Issue**。分解しなければ Issue は1本
- 本文には spec の **Scope lock だけ**を載せる。全文を二重化しない
- 起票は Issue 作成スキルに委譲する

### 6-2. タスクフォルダを作る

フォルダ名は **`#<Issue 番号> <Issue タイトル>`**。

```
.ai/_tasks/#42 受注サマリのキャンセル除外/
├── spec.md
├── progress.json
└── #43 キャンセル済みを金額から除く/     ← 分解した場合。サブ Issue ごと
    └── spec.md
```

Issue 番号を名前に入れるのは、フォルダを見ただけでどの Issue の作業か分かるようにするため。
実行順序は名前ではなく `progress.json` の `tasks` 配列の並びで決まるので、
番号が飛んでいても問題ない。

**Issue を起票しなかった場合**は番号を付けず、合意したタスク名だけにする
（例: `.ai/_tasks/受注サマリのキャンセル除外/`）。

フォルダ名に空白と `#` が入るので、**以後パスを渡すときは必ず引用符で囲む**。

### 6-3. spec と状態ファイルを作る

1. 合意した `spec.md` を書き出す。分解したならタスクごとにも書く
2. `tasks.json` を組み立てる。**`id` はサブタスクのフォルダ名と同じにする**

```json
[{ "id": "#43 キャンセル済みを金額から除く", "title": "キャンセル済みを金額から除く", "issue": 43 }]
```

分解していなければ `[]`。

3. `progress.json` を作る

```bash
node <このスキル>/scripts/state.mjs init --dir ".ai/_tasks/#42 受注サマリのキャンセル除外" --tasks tasks.json
```

4. `agreement` の履歴を追記する

```bash
echo '{"kind":"agreement","task":null,"data":{"summary":"<何に合意したか>","parentIssue":42}}' \
  | node <このスキル>/scripts/state.mjs append --dir ".ai/_tasks/#42 受注サマリのキャンセル除外"
```

準備完了を報告し、実行フェーズへ進んでよいか確認する。
