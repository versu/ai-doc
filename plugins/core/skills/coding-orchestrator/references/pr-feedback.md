# PR のレビューコメントへの対応

読み手はオーケストレーター。

PR を出したあと、人間のレビューで指摘が付くことがある。
**そのタスクを実装したエージェントに直させる**のが原則で、流れは最初の実装とほぼ同じ。

## 最初の実装との違い

| | 最初の実装 | PR フィードバック |
|---|---|---|
| 起点 | spec の Scope lock | **PR に付いた指摘**（Scope lock は変えない） |
| レビューの回数 | `review.roundCap` まで | **1回だけ** |
| レビューの `mode` | 1周目は `full` | **常に `regression`** |
| ブロッカーが出たら | 直して再レビュー | 直して**ユーザーに提示。再レビューはしない** |
| 最後にすること | PR を作る | 既存の PR へ **push**（新しい PR は作らない） |

レビューを1回に絞るのは、対象が「すでにレビューを通った実装への小さな修正」だから。
ここで通常のラウンドを回すと、指摘対応のたびに全体の採点が始まって終わらなくなる。

## 手順

### 1. 指摘の確認と精査

1. PR のコメントを取得する（`gh pr view <番号> --comments`）
2. 指摘ごとに対応するかを検討する
3. **対応する指摘と、対応しない指摘とその理由**を整理し、`AskUserQuestion` で合意を取る。
   指摘が複数あるなら、指摘ごとに「対応する」／「対応しない」を聞く
   （まとめて1問にすると、一部だけ違う判断をしたいときに答えられなくなる）
4. 合意したら `pr-feedback` の履歴を追記する

```bash
echo '{"kind":"pr-feedback","task":"#43 ...","data":{"pullRequest":12,"accepted":["..."],"rejected":["... (理由)"]}}' \
  | node <このスキル>/scripts/state.mjs append --dir ".ai/_tasks/#42 ..."
```

**Scope lock を変える指摘は、その場で実装しない。**
「やらないこと」に踏み込む指摘や、新しい受け入れ条件を足す指摘は、
対応しないと合意するか、**新しいタスクとして切り出す**。
ここを崩すと、PR レビューが仕様変更の入口になって際限がなくなる。

### 2. 実装

`taskStates["#43 ..."].agentId` のエージェントを `SendMessage` で再開し、
対応する指摘を渡して実装を依頼する。

**PR にコメントが付くまでには時間が空くので、再開は失敗しやすい。**
失敗したら、そのタスクの `implementation` 履歴に残した前回の戻り値と spec を添えて
新規に起動する。

### 3. レビューは1回だけ

対応前後の差分（`base` = 対応前の HEAD、`head` = 対応後の HEAD）を `mode: "regression"` で
レビュアーに渡す。問いは「直したことで別の場所が壊れていないか」の1点。

裁定してブロッカーが出たら、実装エージェントに直させ、**その結果を `AskUserQuestion` で
確認してもらう**。ここで再レビューはしない。

### 4. 反映

1. 作業ブランチへ push する（PR は既にあるので新しく作らない）
2. `push` の履歴を追記する
3. 対応した指摘と、対応しなかった指摘の一覧をユーザーに渡す。
   **PR への返信は人間が行う**（こちらは文面を渡すところまで）

### 積み上げているときの注意

後続の PR が既にある場合、**古い PR を直すと後続に影響する**。
push したあと、後続のブランチを rebase する必要があるかをユーザーに確認する。
