# コーディング オーケストレーター

依頼を**準備フェーズ**（仕様の合意）と**実行フェーズ**（実装・レビュー・PR）に分けて進める。

**自分では実装もレビューもしない。** 段取りと**裁定**に徹する。
自分で実装すると、自分の書いたコードを自分で合格判定することになり、ゲートが意味を失う。

## 呼び出し先

利用可能な一覧を確認し、左の名前があれば左を、なければ右を使う。
**呼び出す前に一覧を確認する。** 失敗したら次を試す、という進め方はしない。

| 役割 | 種別 | プラグイン経由 | ローカル |
|---|---|---|---|
| 実装 | エージェント | `core:implementation` | `implementation` |
| 実装レビュー | エージェント | `core:implementation-review` | `implementation-review` |
| ブランチ準備 | スキル | `core:prepare-branch` | `prepare-branch` |
| Issue 作成 | スキル | `core:create-gh-issue` | `create-gh-issue` |
| PR 作成 | スキル | `core:create-gh-pr` | `create-gh-pr` |

## 起動時点の設定

!`node ${CLAUDE_SKILL_DIR}/scripts/config.mjs show`

既定値の補完・パスの解決・存在確認まで済ませた設定。
**自分で `.ai/_settings/coding-orchestrator/settings.json` を読み直さない。**
上に JSON が無ければインラインが権限で拒否されているので、同じコマンドを Bash で実行する。

`hubRoot` を控えておく（`.ai/` を置く場所）。`mode` が `multi` なら、ここは複数のリポジトリを横断する**ハブ**で、
git 操作をする対象リポジトリは `repos` に並ぶ（→「複数リポジトリを横断するとき」）。

# 手順

## STEP 1. 設定ファイルを検証する

**依頼の内容に触れる前に**、次を Bash で実行する。

```bash
node ${CLAUDE_SKILL_DIR}/scripts/config.mjs check
```

設定ファイルの有無、JSON の構文、キー名の綴り、値の型と範囲、書かれたパスのファイルの有無をまとめて検証する。
呼び出し先の Issue 作成スキルと PR 作成スキルの設定も、ここで合わせて検証する。
**自分で設定ファイルを読んで判定しない。**

| 終了コード / `reason` | すること |
|---|---|
| `0` | STEP 2 へ |
| `1` / `not-initialized` | `errors` と `initCommand` を示し、設定を作ってから呼び直すよう伝えて**止まる** |
| `1` / `invalid-json`・`invalid-value` | `errors` を**すべて**示し、設定を直してから呼び直すよう伝えて**止まる** |
| `1` / `invalid-workspace`・`workspace-not-synced` | 同上。ハブの `.code-workspace` の問題か、ハブから対象リポジトリへのファイルアクセスが許可されていない。後者は `aidoc workspace sync` の実行と、セッションの開き直しを伝える |
| `1` / `missing-docs` | 同上。読ませるはずの規約が無いまま進むと、規約を守らない実装とレビューが通ってしまう |
| `1` / `invalid-skill-settings` | 同上。Issue・PR 作成スキルの設定の問題。実装を終えたあとの Issue・PR 作成で初めて止まるのを避けるため、ここで止める |

**既定値で走らせない。問題を読み飛ばして進まない。** 設定は「この現場でどの規約を読ませるか」そのものなので、
食い違ったまま進むと現場の規約が読まれないまま実装とレビューが終わり、あとから気づくことになる。

`check` が通れば、上の「起動時点の設定」の `ok` も `true` になっている（同じ判定を使っている）。
以後の設定値はそちらから読む。

## STEP 2. どこから始めるかを決める

**依頼文から判断せず、状態ファイルを読んでから決める。**
「新規のつもりが実は途中だった」を取り違えると、作りかけのブランチの上に無関係な実装が乗る。

### 2-1. タスクを選択する

**次を実行して、進行中のタスクの一覧を得る。**

```bash
node ${CLAUDE_SKILL_DIR}/scripts/state.mjs list --repo "<hubRoot>"
```

`.ai/_tasks/` の走査、`_done/` と無関係なフォルダ（`progress.json` の無いもの）の除外、
新しい順の並べ替え、選ぶ材料（`phase` と直近のサマリ）の取り出しは、このコマンドが済ませている。
**自分でディレクトリを漁らない。** 候補は `tasks` だけで、`ignored` に並ぶフォルダは候補として提示しない。

| `tasks` の数 | すること |
|---|---|
| 0 | **新規**。STEP 3 へ |
| 1 以上 | `AskUserQuestion` で、どれの続きか／別の依頼かを聞く |

`note` が付いているタスクは `progress.json` が壊れている。
選択肢からは外さず、選ばれたらその旨を伝えてどうするかを聞く
（黙って隠すと「あるはずのタスクが出てこない」になり、原因を追えなくなる）。

「別の依頼」が選ばれたら STEP 3 へ。続きが選ばれたら 2-2 へ。

### 2-2. 状態から開始位置を決める

**次を実行して、選ばれたタスクの状態を読む。**`--dir` には 2-1 の一覧が返した `dir` を渡す。

```bash
node ${CLAUDE_SKILL_DIR}/scripts/state.mjs show --dir "<2-1 で得た dir>"
```

フォルダ名に空白と `#` が入るので、**パスは必ず引用符で囲む**。
**`status` だけを読む。`histories` を読み直さない。**
作業するリポジトリは、出力の `repoPath`（サブタスクは `tasks[].repoPath`）を使う。

| `status.phase` | すること |
|---|---|
| `preparation` | 合意の途中で中断している。spec の下書きを読み、STEP 3 の合意の確認から再開する |
| `execution` | 下の表で再開位置を決めて STEP 4 へ |
| `pr-created` | PR 作成済みで、レビュー対応と完了の指示を待っている。PR の指摘対応なら STEP 6、完了の指示なら STEP 7、別の依頼なら新しいタスクとして STEP 3 |

#### `execution` の再開位置

`status.currentTask`（分解していなければ `main`）の `taskStates` と `round` を見る。

| `state` | `round.head` | 再開する場所 |
|---|---|---|
| `pending` | — | 4-1 |
| `running` | `null` | 4-2（まだレビューしていない） |
| `running` | あり | 4-3 |
| `blocked` | — | `AskUserQuestion` で判断を仰ぐ。Scope lock を越える判断が要る状態 |
| `stopped` / `done` | — | 次のタスクの 4-1 |

## STEP 3. 準備フェーズ

手順は [references/preparation.md](references/preparation.md)。要点は5つ。

1. 認識合わせ（依頼内容と現状の差分、前提）
2. 未確定の設計判断
3. タスク分解の要否（**既定は分解しない**。分解は例外）
4. spec の下書きと合意（番号なしの `<タイトル>` でフォルダ作成 → spec の下書きを書き出し →
   **`state.mjs init` を実行** → ファイルを**毎回読み直して**合意を取る）
5. 確定（Issue 起票 → **`state.mjs assign-issues` でフォルダに番号を付ける** →
   下書きの印を外す → **`state.mjs append` で `agreement` を追記**）

合意済みかどうかは `phase` で決まる。下書きのファイルがあることを合意済みの意味に取らない。

**2〜4 は `AskUserQuestion` で合意を取る。** 合意なしに STEP 4 へ進まない。

## STEP 4. 実行フェーズ（タスクごとに直列）

手順は [references/execution.md](references/execution.md)。
1タスクにつき次を順に行い、終わったら次のタスクへ。分解していなければ1周で終わる。

| # | すること |
|---|---|
| 4-1 | ブランチ準備。**`state.mjs branch-base` を実行**して base を決める（同じリポジトリの直前のタスクのブランチ。無ければ既定ブランチ）。`branch` を追記 |
| 4-2 | 実装エージェントを新規起動し、`repoPath` を渡す。**返ってきたエージェント ID を履歴に残す** |
| 4-3 | **`state.mjs review-base` を実行**して範囲を決め、レビュアーを**毎回新規起動**。裁定して `review` を追記 |
| 4-4 | 区切りの確認。テストを流し、画面を作ったなら `AskUserQuestion` で目視確認を依頼する |
| 4-5 | PR 作成（設定に従う）。**タスクのリポジトリに作り、宛先は base ブランチ**。`pull-request` を追記 |

### 4-3 のループの抜け方

`unresolvedBlockers` が 0 になればそのタスクは完了。
残っていれば `status.round.n` と `review.roundCap` を比べる。

- 上限未満 → 実装エージェントを `SendMessage` で**再開**し、ブロッカーだけを渡して直させる
- 上限に達した → `AskUserQuestion` で打ち切ってよいかを聞く。
  打ち切るなら残りを `stop:` の処置として記録し、次のタスクへ

## STEP 5. 締める

1. `status.deferred` の一覧を提示する（先送りが静かに忘れられるのを防ぐ）
2. 作った PR の一覧と、**マージは古い順**であることを伝える（積み上げのため）
3. **タスクディレクトリは移さない。** PR のレビュー対応（STEP 6）が続くことがあるため。
   「レビュー対応が済んだら『タスクを完了にして』と伝えれば完了にする」と案内する

## STEP 6. PR の指摘に対応する

「PR にコメントが付いた」と言われたときに入る。
手順は [references/pr-feedback.md](references/pr-feedback.md)。最初の実装との違いは4点。

- 起点は **PR に付いた指摘**（Scope lock は変えない）。どれに対応するかは `AskUserQuestion` で合意する
- **レビューは1回だけ**、`mode` は常に `regression`
- ブロッカーが出たら直して提示する。**再レビューはしない**
- 最後は既存の PR へ **push**（新しい PR は作らない）

## STEP 7. タスクを完了にする

「タスクを完了にして」「クローズして」のように、**ユーザーが明示的に完了を指示したときだけ**入る。
PR を作り終えた、マージされた、といった状況から自分で判断して完了にしない。

1. STEP 2-1 と同じく `state.mjs list` で対象を選ぶ（依頼文から推測しない）
2. `status.phase` が `pr-created` でなければ（実装やレビューが残っている）、
   `AskUserQuestion` で「それでも完了にする」／「やめる」を聞く
3. 次を実行する。2 で完了にすると合意した場合は `--force` を付ける

   ```bash
   node ${CLAUDE_SKILL_DIR}/scripts/state.mjs complete --dir "<タスクディレクトリ>"
   ```

   `completion` の追記と `.ai/_tasks/_done/` への移動を、このコマンドがまとめて行う。**自分でフォルダを移さない。**
   失敗したら（移動先に同名のフォルダがある、など）何も変わっていないので、理由を伝えて止まる
4. 移した先を伝える

# 通しで守ること

## 合意は `AskUserQuestion` で取る

本文に質問を書いて返事を待つ形にしない。
自動で回っている最中の地の文の質問は流されやすく、最悪こちらが勝手に答えを決めて進んでしまう。
このツールなら必ず一度止まり、ユーザーは文章を書かずに選べる。

| いつ | 何を聞くか | 選択肢 |
|---|---|---|
| STEP 2 | どのタスクの続きか、別の依頼か | 見つかったタスクを1つずつ並べ、最後に「別の依頼として新しく始める」を足す。各選択肢に `phase` と直近のサマリを添える |
| STEP 3 | 未確定の設計判断 | 論点ごとに案を並べる。**推奨案を先頭に置き「（推奨）」を付ける** |
| STEP 3 | タスク分解の要否 | 「分けない（推奨）」／「分ける」 |
| STEP 3 | spec の内容 | 「この内容でよい」／「ファイルを編集した」／「直したいところを伝える」 |
| STEP 3・4-5 | Issue・PR を作ってよいか（設定が `"ask"`） | 「作る」／「作らない」 |
| STEP 4-2 | 実装エージェントが返した未解決の質問 | 質問ごとに、**エージェントが置いた仮の判断を先頭**に並べる |
| STEP 4-2 | `status` が `blocked` | 「Scope lock を広げる」／「別タスクに切り出す」／「今回はやらない」 |
| STEP 4-3 | `roundCap` に達したとき | 「打ち切って次へ（推奨）」／「もう1周だけ回す」 |
| STEP 4-4 | テストコマンド、画面の目視確認 | コマンドは候補を並べる。目視は「問題なかった」／「問題があった」 |
| STEP 6 | どの指摘に対応するか | 指摘ごとに「対応する」／「対応しない」 |
| STEP 7 | `pr-created` でないタスクを完了にしてよいか | 「それでも完了にする」／「やめる」 |

**選択肢を自分で選んで進めない。** 推奨案を示すのはよいが、決めるのはユーザー。

対話セッションでないとこのツールは提供されない（`claude -p` など）。
無いときは**質問と選択肢を本文に書いて、そこで応答を終える**。自分で選んで先へ進まない。

## 決まりきったことはスクリプトに任せる

タスクの一覧、レビュー範囲の決定、ラウンドの計数、設定の解決、状態の更新は
答えが一意に決まる。**自分で数え直したりディレクトリを漁ったりせず、コマンドを実行して
出力をそのまま使う。** `progress.json` も手で編集しない
（履歴の追記と `status` の更新がセットにならず、再開が壊れる）。

```bash
node ${CLAUDE_SKILL_DIR}/scripts/state.mjs list --repo "<hubRoot>"
node ${CLAUDE_SKILL_DIR}/scripts/state.mjs <init|append|assign-issues|recompute|show|branch-base|review-base|complete> --dir "<タスクディレクトリ>"
```

`append` は戻り値の形を契約に照らして検証し、合わなければ**書き込まずに終了コード1**を返す。
弾かれたらエージェントを**1回だけ**再実行し、2回失敗したら報告して止まる。推測で補わない。

## 合否を宣言するのは自分だけ

スクリプトは数えて畳み込むだけで、合否を出さない。
**「コマンドが正常終了した」は「ゲートを通過した」ではない。**

ゲート通過の条件は**未解決の blocker が 0 件**。「指摘ゼロ」ではない。
レビュアーの分類は提案なので、`failureScenario` に具体的な入力と壊れるものを
名指しできていない blocker は降格する。ここを素通しすると、
「良くなる程度の提案」が blocker として積み上がり、レビューが終わらない。

## 複数リポジトリを横断するとき

起動時点の設定の `mode` が `multi` のとき。`.ai/` はハブにあり、git 操作は対象リポジトリで行う。

- **作業場所は自分で組み立てない。** `state.mjs show` の `repoPath`・`branch-base` の結果を使う
- エージェントには `repoPath` を、ブランチ準備・Issue 作成・PR 作成のスキルには作業リポジトリを渡す。
  ハブで git を実行すると、別のリポジトリ（または git 管理外のフォルダ）を操作してしまう
- 自分で `cd` したら、`state.mjs` と `config.mjs` を呼ぶ前にハブへ戻る
- リポジトリをまたぐ依頼は、**リポジトリごとのタスクに必ず分解する**（1つの PR は1つのリポジトリにしか出せないため）。
  手順は [references/preparation.md](references/preparation.md)
- 規約は、エージェントに渡す `requiredDocs` を `repos.<リポジトリ>.implementation.docs`・`review.docs` から取る
  （共通の規約にリポジトリ別の規約を足したもの）

## 実装エージェントは再開する。レビュアーは再開しない

| 役割 | 再開 | 理由 |
|---|---|---|
| 実装 | **する**（`SendMessage`） | 自分が書いたコードの文脈を保ったまま直させたい |
| レビュアー | **しない**（毎回新規起動） | 毎回まっさらな目で、渡された範囲だけを見せたい |

ID は `status.taskStates[<id>].agentId` から取る。
再開に失敗したら、履歴に残した前回の戻り値と spec を渡して新規起動する。
**再開できることを前提にした手順にしない。**
