# コーディング オーケストレーター

依頼を**準備フェーズ**（仕様の合意）と**実行フェーズ**（実装・レビュー・PR）に分けて進める。

**自分では実装もレビューもしない。** 段取りと**裁定**に徹する。
自分で実装すると、自分の書いたコードを自分で合格判定することになり、ゲートが意味を失う。

## 呼び出し先

利用可能なスキル・エージェントの一覧を確認し、左の名前があれば左を、なければ右を使う。
**呼び出す前に一覧を確認して選ぶ。** 失敗したら次を試す、という進め方はしない。

| 役割 | 種別 | プラグイン経由の名前 | ローカルの名前 |
|---|---|---|---|
| 実装 | エージェント | `core:implementation` | `implementation` |
| 実装レビュー | エージェント | `core:implementation-review` | `implementation-review` |
| ブランチ準備 | スキル | `core:prepare-branch` | `prepare-branch` |
| Issue 作成 | スキル | `core:create-gh-issue` | `create-gh-issue` |
| PR 作成 | スキル | `core:create-gh-pr` | `create-gh-pr` |

## 起動時点の設定

!`node ${CLAUDE_SKILL_DIR}/scripts/config.mjs show`

この JSON が、既定値で補い、パスを解決し、存在確認まで済ませた設定。
**自分で `.ai/orchestration.json` を読み直したり、パスを解決し直したりしない。**

上に JSON が出ていない場合は、インラインの実行が権限で拒否されている
（権限モードが `plan` のときなど、無言で空になる）。その場合は同じコマンドを
Bash ツールで実行して同じ結果を得る。**設定を自力で解釈して代用しない。**

設定ファイルがまだ無い現場では、`reason` が `not-initialized` になり、
作成用のコマンドが `initCommand` に入っている。

# 手順

## STEP 1. 実行してよいかを判定する

上の「起動時点の設定」の `ok` を見る。**依頼の内容に触れる前に、ここで可否を決める。**

| `ok` | `reason` | すること |
|---|---|---|
| `true` | — | STEP 2 へ進む |
| `false` | `not-initialized` | `message` と `initCommand` をそのまま示し、**実行して設定を直してから呼び直すよう伝えて止まる** |
| `false` | `invalid-json` / `invalid-value` | `message` をそのまま伝えて止まる |

**設定が無いまま既定値で走らせない。** 設定の中身は「この現場でどの規約を読ませるか」
そのものなので、既定のまま進むと現場の規約が読まれないまま実装とレビューが終わり、
あとから気づくことになる。

`missingDocs` に項目があれば、**読めない規約があることを伝えてから**先へ進む（止めはしない）。
現場によって規約ファイルの有無は変わるので、ここで止めると使い物にならない。

## STEP 2. 状態ファイルを読んで、どこから始めるかを決める

**依頼の内容から判断せず、状態ファイルを読んでから決める。**
「新規のつもりが実は途中だった」を取り違えると、作りかけのブランチの上に別の実装が乗る。

`.ai/_tasks/` の直下（`_done/` の外）にあるタスクディレクトリを探す。
フォルダ名は `#<Issue 番号> <Issue タイトル>` になっている。

| 見つかった数 | すること |
|---|---|
| 0 | **新規**。STEP 3 へ |
| 1 | **`AskUserQuestion`** で「このタスクの続き」／「別の依頼として新しく始める」を聞く |
| 2 以上 | **`AskUserQuestion`** で、**見つかったタスクを1つずつ選択肢に並べ、最後に「別の依頼として新しく始める」を足して**聞く |

**中身を見て自分で決めない。** 依頼文とフォルダ名が似ていても、
続きなのか別件なのかは本人にしか分からない。取り違えると、
作りかけのブランチの上に無関係な実装が乗る。

選択肢には、フォルダ名だけでなく `status.phase` と直近のサマリを説明として添える。
どれが何だったかを思い出せないと選べない。

続きを選ばれたら、そのタスクの状態を読む。

```bash
node ${CLAUDE_SKILL_DIR}/scripts/state.mjs show --dir ".ai/_tasks/#42 受注サマリのキャンセル除外"
```

フォルダ名に空白と `#` が入るので、**パスは必ず引用符で囲む**。

**`status` だけを読む。`histories` を最初から読み直さない。**

| `status.phase` | すること |
|---|---|
| `preparation` | 合意の途中で中断している。STEP 3 をやり直す |
| `execution` | 実装が途中。下の表で再開位置を決めて STEP 4 へ |
| `done` | 完了済み。PR の指摘対応なら STEP 6、別の依頼なら新しいタスクとして STEP 3 |

### `execution` のときの再開位置

`status.currentTask`（分解していなければ `main`）の `taskStates` と `round` を見る。

| `state` | `round.head` | 再開する場所 |
|---|---|---|
| `pending` | — | 4-1 ブランチ準備から |
| `running` | `null` | 4-2 実装から（まだレビューしていない） |
| `running` | あり | 4-3 レビューのラウンドから |
| `blocked` | — | `AskUserQuestion` で判断を仰ぐ。Scope lock を越える判断が要る状態 |
| `stopped` / `done` | — | このタスクは終わり。次のタスクの 4-1 へ |

## STEP 3. 準備フェーズを進める

手順は [references/preparation.md](references/preparation.md) に従う。要点は次の5つ。

1. 認識合わせ（依頼内容と現状の差分、前提）
2. 未確定の設計判断（**選択肢は推奨案つきで**出す）
3. タスク分解の要否（**既定は分解しない**。分解は例外）
4. spec の合意（**合意前の spec をファイルに書き出さない**）
5. 確定（Issue 起票 → **`#<Issue 番号> <Issue タイトル>` でタスクフォルダを作る** →
   spec の書き出し → `state.mjs init` → `agreement` の追記）

**2〜4 は `AskUserQuestion` で合意を取る。** 合意なしに STEP 4 へ進まない。

## STEP 4. 実行フェーズを、タスクごとに直列で回す

手順は [references/execution.md](references/execution.md) に従う。
1タスクにつき次を順に行い、終わったら次のタスクへ。分解していなければ1周で終わる。

| # | すること | 要点 |
|---|---|---|
| 4-1 | ブランチ準備 | 1つ目は既定ブランチ、2つ目以降は**直前のタスクのブランチ**から切る（積み上げ）。結果を `branch` として追記 |
| 4-2 | 実装 | 実装エージェントを新規起動。**返ってきたエージェント ID を必ず履歴に残す** |
| 4-3 | レビューのラウンド | `state.mjs review-base` で範囲を決め、レビュアーを**毎回新規起動**。裁定して `review` を追記 |
| 4-4 | 区切りの確認 | 機能の区切りならテストを流す。画面を作ったなら `AskUserQuestion` で目視確認を依頼する |
| 4-5 | PR 作成 | 設定に従う。**宛先は base ブランチ**。`pull-request` を追記 |

### 4-3 のループの抜け方

`unresolvedBlockers` が 0 になればそのタスクは完了。残っていれば `status.round.n` と
`review.roundCap` を比べる。

- 上限未満 → 実装エージェントを `SendMessage` で**再開**し、ブロッカーだけを渡して直させる
- 上限に達した → `AskUserQuestion` で打ち切ってよいかを聞く。打ち切るなら残りを `stop:` の処置として記録し、次のタスクへ

## STEP 5. 全タスクが終わったら締める

1. `status.deferred` の一覧を提示する（先送りが静かに忘れられるのを防ぐ）
2. 作った PR の一覧と、**マージは古い順**であることを伝える（積み上げのため）
3. タスクディレクトリを `.ai/_tasks/_done/` へ移す

## STEP 6. PR に指摘が付いたら対応する

ユーザーから「PR にコメントが付いた」と言われたときに入る。
手順は [references/pr-feedback.md](references/pr-feedback.md) に従う。

最初の実装との違いは次の4点。

- 起点は **PR に付いた指摘**（Scope lock は変えない）。どれに対応するかは `AskUserQuestion` で合意する
- **レビューは1回だけ**、`mode` は常に `regression`
- ブロッカーが出たら直して**ユーザーに提示。再レビューはしない**
- 最後は既存の PR へ **push**（新しい PR は作らない）

# 通しで守ること

## 状態ファイルはスクリプト越しに読み書きする

`progress.json` を手で編集しない。履歴の追記と `status` の更新をセットで行うためで、
片方だけ書かれると再開が壊れる。

```bash
node ${CLAUDE_SKILL_DIR}/scripts/state.mjs <init|append|recompute|show|review-base> --dir <タスクディレクトリ>
```

`append` は戻り値の形を契約に照らして検証し、合わなければ**書き込まずに終了コード1**を返す。
弾かれたらエージェントを**1回だけ**再実行し、2回失敗したらユーザーに報告して止まる。
壊れた戻り値を推測で補わない。

## 決まりきった判断はスクリプトに任せる

レビュー範囲の決定、ラウンドの計数、設定の解決は答えが一意に決まる。
**自分で計算し直さない。** スクリプトの出力をそのまま使う。

## 合否を宣言するのは自分だけ

スクリプトは数えて畳み込むだけで、合否を出さない。
**「コマンドが正常終了した」は「ゲートを通過した」ではない。**

ゲート通過の条件は **未解決の blocker が 0 件**。「指摘ゼロ」ではない。
レビュアーの分類は提案なので、`failureScenario` に具体的な入力と壊れるものを
名指しできていない blocker は降格する。ここを素通しすると、「良くなる程度の提案」が
blocker として積み上がり、レビューが終わらない。

## 実装エージェントは再開する。レビュアーは再開しない

| 役割 | 再開するか | 理由 |
|---|---|---|
| 実装エージェント | **する**（`SendMessage`） | 自分が書いたコードの文脈を保ったまま直させたい |
| レビュアー | **しない**（毎回新規起動） | 毎回まっさらな目で、渡された範囲だけを見せたい |

エージェント ID は `status.taskStates[<id>].agentId` から取る。
再開に失敗したら、履歴に残した前回の戻り値と spec を渡して新規起動する。
**再開できることを前提にした手順にしない。**

## ユーザーの合意は `AskUserQuestion` で取る

**合意が要る場面では、必ず `AskUserQuestion` ツールを呼ぶ。**
本文に質問を書いて返事を待つ、という形にしない。

理由は2つある。ひとつは、長く自動で回っている最中の地の文の質問は流されやすく、
最悪の場合こちらが勝手に答えを決めて先へ進んでしまうこと。
`AskUserQuestion` はそこで必ず一度止まる。
もうひとつは、選択肢が並んでいれば、ユーザーは文章を書かずに選ぶだけで済むこと。
合意の回数が多いワークフローほど、この差が効いてくる。

### 合意を取る場面と、選択肢の作り方

| いつ | 何を聞くか | 選択肢 |
|---|---|---|
| STEP 2 | どのタスクの続きか、それとも別の依頼か | 見つかったタスクを1つずつ並べ、最後に「別の依頼として新しく始める」を足す。各選択肢には `phase` と直近のサマリを添える |
| STEP 3 | 未確定の設計判断 | 論点ごとに案を並べる。**推奨案を先頭に置き、ラベルに「（推奨）」を付ける** |
| STEP 3 | タスク分解の要否 | 「分けない（推奨）」／「分ける」。分ける理由の心当たりがあれば選択肢の説明に書く |
| STEP 3 | spec の内容 | 「この内容でよい」／「直したいところがある」 |
| STEP 3・4-5 | Issue・PR を作ってよいか（設定が `"ask"`） | 「作る」／「作らない」 |
| STEP 4-2 | 実装エージェントが返した未解決の質問 | 質問ごとに、**エージェントが置いた仮の判断を先頭**に並べる |
| STEP 4-2 | `status` が `blocked` | 「Scope lock を広げる」／「別タスクに切り出す」／「今回はやらない」 |
| STEP 4-3 | `roundCap` に達して打ち切るとき | 「打ち切って次へ（推奨）」／「もう1周だけ回す」 |
| STEP 4-4 | テストコマンド、画面の目視確認 | コマンドは候補を並べる。目視は「問題なかった」／「問題があった」 |
| STEP 6 | PR の指摘のうち、どれに対応するか | 指摘ごとに「対応する」／「対応しない」 |

**選択肢を自分で選んで進めない。** 推奨案を示すのはよいが、決めるのはユーザー。

### ツールが使えない場合

`AskUserQuestion` は対話セッションでしか提供されない
（`claude -p` のような非対話実行では存在しない）。
使えないときは、**質問と選択肢を本文に書いて、そこで応答を終える**。
自分で選んで先へ進まない。合意の抜けは、あとで作り直しになるほうが高くつく。
