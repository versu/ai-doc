# Issue の作成

## 参照

Issue 本文の書き方と雛形（規約が変わればここだけ直せばよい）。

[references/issue-template.md](references/issue-template.md)

## 渡されるもの

| 項目 | 省略時 |
|---|---|
| タイトル | 本文から起こしてユーザーに確認する |
| 本文（または spec のパス） | ユーザーに確認する |
| 親 Issue の番号 | 親を持たない Issue として作る |
| ラベル | 付けない |
| 担当者 | **自分（`@me`）を設定する** |

担当者を空のまま起票すると、あとで一覧を見たときに誰が抱えているのか分からなくなる。
依頼を受けて起票する以上、着手するのは自分なので、既定で自分を割り当てる。
別の人に持たせたい場合だけ、呼び出し側から指定してもらう。

## 手順

### 1. 前提を確認する

```bash
gh auth status
```

未認証なら**作成せずに理由を報告して止まる**。

### 2. 本文を組み立てる

[references/issue-template.md](references/issue-template.md) に従う。

### 3. 内容を提示して合意を取る

**内容を見せずに作らない。** `AskUserQuestion` で次を選んでもらう。

| 選択肢 | すること |
|---|---|
| **OK** | 提示した内容でそのまま作成する |
| **内容を出力** | ファイルに書き出す。ユーザーが直接編集できるようにするため |

「内容を出力」が選ばれたときの流れ。

1. **タスクフォルダに書き出す。** 既定は `.ai/_tasks/<タスク名>/issue-<タスクid>.md`。
   タスクフォルダが分からなければ出力先を聞く
2. ユーザーが編集する
3. **もう一度「このファイルの内容で作成してよいか」を確認する**
4. 承認されたら、**ファイルの現在の内容**をそのまま使って作成する。
   提示したときの内容を使い回さない（編集を取りこぼすため）
   - **1行目の `# ` 見出しをタイトル**、それ以降を本文として扱う

### 4. 作成する

```bash
gh issue create --title "<タイトル>" --body-file <path> --assignee "@me"
```

- `--assignee "@me"` で自分を担当者にする。**指定が無いかぎり必ず付ける**
- 親を指定するときは `--parent` を足す（次節の条件を満たす場合）

## サブ Issue

`gh` 2.94.0 で Issues 2.0 対応が入り、サブ Issue をオプションで直接作成できる。

| やりたいこと | コマンド |
|---|---|
| 親を指定して子 Issue を作る | `gh issue create --parent <親の番号>` |
| 既存の Issue を後から子にする | `gh issue edit <親の番号> --add-sub-issue <子の番号>` |

**必要条件**: `gh` 2.94.0 以上、かつ GitHub.com または GHES 3.17 以上。

使う前に確認する。

```bash
gh --version
```

### 満たさないときのフォールバック

サブ Issue の関係は設定せず、**子 Issue の本文の先頭に `Parent: #<親の番号>` を書いてリンクする**。
そのうえで「`gh` を 2.94.0 以上に上げるとサブ Issue として登録できる」と一度だけ伝える。

この分岐はこのスキルの中に閉じる。呼び出し側には「親を指定して作る」だけに見せる。

## 返すもの

作成した Issue の番号。フォールバック経路を通ったならその旨も添える。

## 単体で使うとき

「この不具合を Issue にして」のように呼ばれたら、本文を組み立てて手順3から進める。
タスクフォルダが無い場合、「内容を出力」の出力先はユーザーに聞く。
