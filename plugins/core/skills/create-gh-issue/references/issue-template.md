# Issue 本文の雛形

読み手は Issue を作るエージェント。

## 方針

**spec の全文を貼らない。** Issue と spec の二重管理になり、必ず食い違う。
Issue に置くのは**背景と合意の要点（Scope lock）だけ**にする。設計判断・影響範囲は載せない。

Scope lock だけでは「なぜやるのか」が伝わらず、Issue を読んだ人が目的の妥当性を判断できない。
そのため冒頭に背景を置く。背景は spec の「背景・経緯」の「なぜやるのか」から取り、
ドメイン用語で書く（コード上の識別子や、調査中に使っていた呼び名を持ち込まない）。
spec が無いときは、渡された本文や依頼内容から起こす。

仕様そのものへの導線は書かなくてよい。タスクフォルダの名前が
`#<Issue 番号> <Issue タイトル>` になっているので、Issue 番号から辿れる。

## 雛形

```markdown
# <タイトル。何を実現するかを1行で>

## 背景
（なぜこの変更が必要か。いま困っていること、きっかけ。数文）

## 目的
（spec の Scope lock の「目的」）

## やらないこと
- （spec の Scope lock の「やらないこと」）

## 受け入れ条件
- [ ] （spec の Scope lock の「受け入れ条件」をそのまま）
```

サブ Issue の背景は、親の背景を繰り返さない。**親のうち、このタスクが担う部分**を1〜2文で書く。

サブ Issue でフォールバック経路を使う場合は、先頭に1行足す。

```markdown
Parent: #<親の番号>
```

## タイトル

- 何を実現するかを書く。手段ではなく結果
- 接頭辞（`feat:` など）は付けない。コミットメッセージとは別物
