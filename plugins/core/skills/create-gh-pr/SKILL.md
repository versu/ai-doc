# Pull Request の作成

## 参照

| 内容 | 参照先 |
|---|---|
| 本文の雛形 | [references/pr-template.md](references/pr-template.md) |
| 本文の書き方（**必ず読む**） | [references/pr-writing.md](references/pr-writing.md) |

書き方を別ファイルにしているのは、手順が変わるときと、文章の基準が変わるときが
別のタイミングだから。基準を直したいときに手順を読み直さなくてよいようにしている。

## 渡されるもの

| 項目 | 省略時 |
|---|---|
| 宛先（base）ブランチ | リポジトリの既定ブランチ |
| タイトル | 本文から起こしてユーザーに確認する |
| 本文（または spec と Issue 番号） | spec と直近のコミットから組み立てる |
| draft か否か | draft にしない |

**宛先は呼び出し側が渡す。** 積み上げ（stacked PR）では直前のタスクのブランチになる。

## 手順

### 1. 前提を確認する

```bash
gh auth status
git status --porcelain     # 未コミットの変更が無いこと
git log --oneline <base>..HEAD   # コミットが1つ以上あること
```

どれかを満たさなければ**作成せずに理由を報告して止まる**。

### 2. 本文を組み立てる

[references/pr-template.md](references/pr-template.md) の構成に従い、
[references/pr-writing.md](references/pr-writing.md) の書き方を守る。

### 3. 内容を提示して合意を取る

**内容を見せずに作らない。** `AskUserQuestion` で次を選んでもらう。

| 選択肢 | すること |
|---|---|
| **OK** | 提示した内容でそのまま作成する |
| **内容を出力** | ファイルに書き出す。ユーザーが直接編集できるようにするため |

「内容を出力」が選ばれたときの流れ。

1. **タスクフォルダに書き出す。** 既定は `.ai/_tasks/<タスク名>/pr-<タスクid>.md`。
   タスクフォルダが分からなければ出力先を聞く
2. ユーザーが編集する
3. **もう一度「このファイルの内容で作成してよいか」を確認する**
4. 承認されたら、**ファイルの現在の内容**をそのまま使って作成する。
   提示したときの内容を使い回さない（編集を取りこぼすため）
   - **1行目の `# ` 見出しをタイトル**、それ以降を本文として扱う

### 4. 作業ブランチを push する

**合意が取れてから push する。** 先に push すると、内容を見たユーザーが
「やっぱりやめる」と言ったときに、リモートに中途半端なブランチだけが残る。

```bash
git push -u origin HEAD
```

### 5. 作成する

```bash
gh pr create --base <宛先ブランチ> --title "<タイトル>" --body-file <path>
```

## 停止条件

| 条件 | 理由 |
|---|---|
| `gh` が未認証 | 作れないため |
| 未コミットの変更がある | PR の差分に入らない変更が手元に残るため |
| `<base>..HEAD` にコミットが無い | 空の PR になるため |
| push できない | リモートに反映されないため。**合意のあとに push するので、ここで止まったら PR は作らない** |

## 返すもの

作成した PR の番号。宛先が既定ブランチでない場合は、**マージ順**もあわせて伝える。

## 単体で使うとき

「この変更で PR 出して」のように呼ばれたら、spec が無くても
直近のコミットと差分から本文を組み立て、手順3から合意を取る。
