# PR 本文の書き方

読み手は PR を作るエージェント。ここに書いてあるのは文章の基準。

## 前提 — 読むのは人間

**PR をレビューするのは人間で、この変更の背景を知らない可能性がある。**
差分を読めば分かることを繰り返すのではなく、差分からは分からないこと
（なぜ必要か、何が変わるか、どう確かめるか）を書く。

## 規約

### システム内部の用語ではなく、ドメイン用語で書く

クラス名・メソッド名・内部の呼び名をそのまま持ち込まない。
レビュアーがそのコードを知らなければ、内部名は情報を運ばない。

| ❌ | ⭕ |
|---|---|
| `RegisterService` に `enabled` チェックを追加 | 無効にしている取引先には、担当者を登録できないようにした |
| `NotificationDispatcher` の呼び出しを `try` の外へ移動 | 登録に失敗してやり直したとき、通知が二重に飛ばないようにした |

### DB のテーブル名・カラム名はそのまま使う

ここだけは言い換えない。レビュアーが実物と突き合わせるときに、名前が違うと照合できないため。
ただし**初出のときに一度だけ**括弧書きで意味を添える。

> `orders`（受注）テーブルに `canceled_at`（キャンセル日時）を追加した。
> 以降、`canceled_at` が入っている受注は月次集計から除く。

2回目以降は括弧を付けない。毎回付けると読みにくくなる。

### 「何をしたか」より先に「なぜ必要か」を書く

| ❌ | ⭕ |
|---|---|
| 登録処理に重複チェックを追加した | 同じ受注が二重に計上されていたため、登録時に重複を弾くようにした |

### 略語・社内用語は初出で開く

> WMS（倉庫管理システム）から受け取った在庫数を…

### 差分を見れば分かることを繰り返さない

変更したファイルの列挙や、コードのそのままの引用は書かない。
GitHub の差分表示のほうが正確で読みやすい。

## 迷ったときの目安

**その現場に来て1週間の人が読んで、何が変わるのか・どこを見ればよいかが分かるか。**
分からなければ、内部用語が残っているか、背景の説明が足りていない。
