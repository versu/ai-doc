# テクニカルライティング規約

読み手は、技術文書を**書く**エージェントと**レビューする**エージェント。
ここに書いてあるのは、どちらにも共通する文章の基準。書くときは守る基準として、レビューするときは指摘の観点として使う。

## 読者の基準

**専門外の技術読者・他部署のエンジニアが読んで、途中の一語で詰まらないか**を基準にする。

書き手は自分の知っていることを「誰でも知っている」と思い込みやすい（知識の呪い）。
たとえば「SaaSにおけるMRRは重要です」だけでは、MRR が何かを知らない社外の読者が置き去りになる。

文書の種類によって、想定する読者と重視する点が変わる。

| 文書の種類 | 想定する読者 | 重視する点 |
|---|---|---|
| 技術記事・技術書 | 話題に初めて触れる技術者（社外を含む） | 用語の説明、手法を選んだ理由、読み通せる流れ |
| 設計書 | 後から保守・レビューする開発者 | 決定の理由と却下した案、前提と制約 |
| README | 初めてそのリポジトリを触る開発者 | 何ができるか、動かすまでの最短手順 |
| 手順書 | その作業を初めて行う担当者 | 手順の順序、前提条件、各手順の結果の確かめ方 |

## 文体

- 語尾・文体は自由。「です・ます」と「だ・である」が章や著者で分かれていてもよい。フランクな書き方も構わない
- **唯一の NG は過度なキャラ付け**（「〜でござる」「〜だお」など、品位を損なう表現）

## 用語

### 初出で説明する

次のものは、**初出の箇所（見出し・キャプションを含む）またはそれより前**で説明する。
説明はフルスペル・言い換え・脚注・1文の補足のいずれでもよい。

- 略語・頭字語（LVLM, IoU, mAP など）
- モデル名・製品名・ライブラリ名・データセット名（Qwen, Playwright など）
- タスク名・手法名・評価指標名（ファインチューニング, bounding box など）
- ドメイン固有表現・帳票用語（明細表, 多段ヘッダ など）
- 著者独自の定義語（「3点セット」など）

### 説明が要るかの線引き

| 区分 | 例 |
|---|---|
| 説明不要 | AI, API, HTML, PDF, URL, OS, ID, GPU, OSS, JSON, CSS |
| 説明が必要 | 特定分野のモデル・ライブラリ名、評価指標、業務ドメイン固有の表現、社内用語、著者独自の定義 |

頭字語は、一般常識レベルのものを除き、初出でフルスペル（原語）を示す。

### 表記をそろえる

同じ概念には同じ言葉を使う（「精度」と「正解率」を混用しない）。
言葉が変わると、読者は別の概念だと受け取る。

## 文

- 主語と述語が対応している。長い文や入れ子の多い文でねじれていない
- 誤字・脱字・衍字がない

## 表記

句読点のスタイル（「、。」か「，．」か）を文書全体で統一する。

## 論理構成

- 主張には根拠がある。論の飛躍がない
- 断定の強さが、データや実績と釣り合っている
- その手法・モデル・評価指標を**なぜ選んだか**の理由がある

## 全体構成

- 冒頭で述べた主張と、まとめの主張がずれていない
- 節ごとの記述の粒度（詳細さ）がそろっている
- 離れた場所で同じ説明を繰り返していない

## 図表

- すべての図表にタイトルまたはキャプションがある
- すべての図表を本文から一度は参照している（孤立した図表を作らない）
- 本文だけで読み解ける。色・凡例・ラベルの意味が書かれている
- キャプションと地の文で、まったく同じ説明を重複させない
- 本文で述べた概念（ラベル体系など）と、図表・具体例の内容が対応している
